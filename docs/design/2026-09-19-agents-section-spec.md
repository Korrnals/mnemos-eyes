# Спека раздела «Агенты» — v1 (+ фундамент north-star)

> Status: **на ратификации АРХКОМ-4** (2026-09-19, вердикт UI/UX Designer,
> зафиксирован TL). Продукт-спека, не UI-код.
> Расширяет: концепт `2026-09-web-app-redesign-concept.md` §2.1/§3.3/§4.4,
> ADR 0009 (+Amendment 2), ADR 0005, `ui-contract.md` §11.
> Плотность: весь раздел — операционный режим (dense): строка 32–36px,
> `--text-sm`, моно для id/таймеров.

## 0. Модель и терминология (новая сущность — обязательна до UI)

| Термин | Что это | Пример |
| --- | --- | --- |
| **Харнес** (harness) | тип среды исполнения | `zcode`, `hermes`, `copilot` |
| **Специалист** (specialist) | роль/компетенция | `gcw-frontend-developer` |
| **Исполнитель** (executor) — новый | конкретный подключённый экземпляр: харнес × среда × точка подключения; присутствие, возможности (allowlist-маппинги), транспорт | `zcode@laptop` (local), `zcode@mesh-2` (mesh) |

Слово «агент» в UI-строках раздела не используется (размывает фиксацию
ADR 0005). «Поручение» = assignment (RU-строки; EN — assignment).

## 1. Структура раздела

```
Агенты /agents
├── Исполнение    /agents/execution          — живое исполнение (стартовая)
├── Специалисты   /agents/specialists        — реестр ролей + /:name (профиль)
└── Харнесы·среды /agents/harnesses          — типы харнесов, среды, реестр исполнителей
```

**`/agents` — алиас на `/agents/execution`**, не отдельная обзорная страница:
главный вопрос раздела «кто чем занят прямо сейчас»; сводка из счётчиков —
дашификация (запрещена концептом §2.4). Обзор домена уже живёт в блоке
«Агенты» на Home.

### 1.1 `/agents/execution` — три слоя

1. **Полоса исполнителей** (presence strip, ~64px): чип на исполнителя — точка
   присутствия, транспорт (local/mesh), счётчик активной работы, возраст
   пульса. Клик — фильтр поручений. Единственный «смелый» элемент раздела;
   зародыш north-star-офиса: присутствие = персонажи в комнате.
2. **Список поручений** (dense-таблица): группы `активные (claimed+running)` →
   `очередь` → `терминальные за сегодня` (свёрнуты, персистентно, не
   рендерятся при нуле). Строка: state-бейдж · T-id+заголовок (ссылка) ·
   специалист · исполнитель/маршрут · heartbeat/возраст (моно). Фильтры:
   state-чипы, исполнитель, специалист, поиск.
3. **Панель UI-10** (нижняя, раскрываемая, персистентная): сквозная лента
   событий исполнения (assignment.* + отчёты, интерливинг, actor-подписи);
   на `/tasks/:id` — тот же компонент в скоупе задачи.

Детали поручения — **дровер** (подглядывание), не роут: таймлайн
created→claimed→started→пульсы→терминал, строка идентичности, шапка конверта
(`[GCW ASSIGNMENT …]` + `MODE:`), hash снапшота (моно), превью финального
отчёта. Assignment не получает свой роут — это метаданные исполнения задачи,
не мастер-сущность (ADR 0009 §6).

Первый экран отвечает: **кто подключён → что делает сейчас (честный возраст
пульса) → что застряло в очереди.** Нет графиков, нет счётчиков ради
счётчиков, пустые группы не рендерятся.

## 2. Состояния честности

### 2.1 Присутствие исполнителя (из TTL пульса, не из оптимизма)

| Состояние | Условие (константы сервера) | Вид |
| --- | --- | --- |
| **online** | пульс ≤ 2 мин | iris-точка + «онлайн» |
| **stale** | 2–10 мин | amber-точка + «пульс пропущен N мин» |
| **offline** | > 10 мин или дерегистрация | нейтральная полая точка + «не на связи, последняя связь N мин назад» |

**Правило двух часов**: присутствие исполнителя и жизнь поручения —
независимые факты; UI показывает оба, никогда не схлопывая (чип «исполнитель
не на связи 12 мин» + строка «running, пульс 12 мин назад, истечёт через
~18 мин» — превентивный отсчёт). Зелёный — только по свежему факту, amber —
только при реальном пропуске.

### 2.2 Identity «reported by X (unverified)»

Контурный (незаполненный) чип + tooltip «Личность заявлена исполнителем,
сервером не проверена». Нейтральный тон: unverified ≠ подозрительно.
Резервируется визуальный слот: при T1–T3 чип получает заполнение + галку без
редизайна языка.

### 2.3 Default-executor UX

- **Где задаётся (v1)**: один глобальный дефолт + один fallback —
  `/system/settings` → «Исполнение». Проектный override — отложен (при ≥2
  исполнителях с разной специализацией); структура данных резервируется.
- **В момент назначения**: шаг выбора (специалист → исполнитель «По
  умолчанию» | конкретный; offline видим, но disabled с причиной) +
  **живое превью маршрута**: целевой / дефолтный / без маршрута («Нет
  доступного исполнителя… Поручение будет ждать в очереди» — кнопка активна,
  ожидание честно).
- **Никакой тихой подмены**: превью показывает правило, факт показывает
  `claimed_by`; перенаправление после создания НЕ производится.
- **Дефолт недоступен**: поручение в `queued` с видимым возрастом и чипом
  «ждёт исполнителя»; действия владельца: выбрать другого, отменить, ждать.
  at-most-once-семантика не маскируется.

### 2.4 Граница с доменом «Задачи»

Задача — объект работы (что); раздел — исполнение (кто/как/когда). Карточка
задачи: бейдж → `/tasks/:id` таб «Исполнение» (вся глубина поручений задачи,
триггер «Взять в работу», отмена, повтор). Создание поручений — **только** на
задаче; раздел — observability + отмена/повтор. Отмена running: confirm
«исполнителю будет отправлен сигнал остановки», toast «отмена отправлена»
(асинхронность честна).

## 3. State-матрицы

### 3.1 Поручение — 7 состояний

| Состояние | Вид строки | Сигналы |
| --- | --- | --- |
| `queued` | нейтральный контур-бейдж + возраст (моно) | чип «ждёт исполнителя» при offline-цели |
| `claimed` | iris-контур + «взято N мин назад» + исполнитель (unverified-чип) | >10 мин без старта → amber + отсчёт до истечения |
| `running` | iris + пульс-точка + «пульс N мин назад» | пульс >2 мин → amber; приближение к 30-мин reaper → отсчёт |
| `done` | приглушённо-success + ссылка на финальный отчёт | tooltip с отчётом |
| `failed` | error + причина из fail-отчёта | CTA «Отчёт» и «Перезапустить» (префилл) |
| `cancelled` | приглушённый нейтральный | причина/время в tooltip |
| `expired` | warning («истёк: нет пульса/старта») | CTA «Перезапустить»; механика reaper в tooltip |

Все статусы: цвет + текст + форма (WCAG 1.4.1); терминальная приглушённость
держит контраст ≥ 4.5:1.

### 3.2 Интерактивные компоненты (канон hover/focus/active/disabled/error/loading/empty)

- Чип исполнителя: hover → tooltip (возможности, транспорт, последняя связь);
  offline-чип кликабелен (история поручений исполнителя); точка присутствия
  имеет текстовый label для скринридеров.
- Строка поручения: hover — только фон; `j/k` навигация, `Esc` закрывает
  дровер; контекст-меню: открыть задачу / отменить / копировать id.
- Панель UI-10: collapsed по умолчанию; новые события — подсветка-затухание
  2с без движения строк; `aria-live=off`, aloud — только терминальные
  переходы; empty: «Событий исполнения пока нет — возьмите задачу в работу».
- «Взять в работу»: матрица А концепта §4.4 + выбор исполнителя + превью
  маршрута; ошибки 409/429/403 — текст из API.
- Пустые состояния с действием: нет исполнителей → «Запустите поллер —
  инструкция»; нет поручений → подсказка входа.
- SSE-разрыв: amber-маркер «данные на HH:MM» только при лежащем сокете;
  после reconnect — re-fetch поручений и исполнителей.
- Motion: без амбиентной анимации; entrance полосы ≤3 чипов, 200ms;
  `prefers-reduced-motion` гасит всё.
- Токены: только семантические алиасы (`--presence-online/stale/offline` →
  существующие iris/warning/muted); **новых цветов нет** (ADR 0003).

## 4. Принципы эволюции к north-star («Живой офис»)

Фундамент закладываем, офис не проектируем:

1. **Исполнитель — первичная визуальная сущность, не фильтр**: полоса
   присутствия никогда не деградирует в dropdown.
2. **Событие — нарратив, не счётчик**: UI-10 хранит грамматику
   (кто · действие · объект · время); офис будет проекцией этой ленты,
   события не сжимаются в агрегаты.
3. **Данные резервировать сейчас**: стабильные id исполнителей (не имена),
   история присутствия (last-seen trail), история поручений по исполнителю,
   возможности как структура (маппинги, не free text).
4. **Слот аватара** в чипе и профиле — пустой в v1 (без декоративных блобов
   и emoji), геометрия зарезервирована.
5. **Живость = реальные сигналы**: никаких псевдо-эмоций и idle-анимаций
   «думает»; офис показывает факты.
6. **Проекционная независимость**: список и офис — две проекции одного state;
   семантика не привязана к геометрии.
7. **Колодец уже есть**: якорь памяти (Home-герой) — единая метафора;
   активность исполнителей связывается с пульсом памяти (отчёты → записи).
8. **Ловушки**: дашификация, геймификационный шпон (уровни/XP), тихая
   подмена исполнителя, больше одного амбиентного движения.

Персонификация гейтована T1–T3 (ADR 0009 §8): персонажи поверх
unverified-строк — доверительный театр. Запреты до триггеров: чат-слой,
симулированное присутствие, agent-initiated UI-действия сверх нотификаций.

## 5. Требования к контрактам (для SE)

1. `GET /api/executors`: стабильный `id`, name, harness, transport
   (`local|mesh`), capabilities (allowlist-маппинги), `registered_at`,
   `last_seen_at`, declared identity. TTL-константы (2/10 мин)
   документируются сервером, UI не гадает.
2. SSE `executor.*`: эмит только при **смене** состояния присутствия; payload
   `{executor, prev_state, state, last_seen_at}`.
3. Assignment-поля (additive): аннотация `routing` (`resolved`, `reason`) в
   GET-ответе (вычисляется, не хранится); `executor_id` (explicit-таргет).
4. Настройка дефолта: `GET/PUT /api/settings/execution` (default + fallback;
   поле scope — резерв под per-project).
5. Фильтры списка (правка 2026-09-21 по факту контракта сервера):
   `GET /api/assignments?state=&task_id=` — точные фильтры сервера;
   `executor_id=` — presence-piggyback при опросе исполнителем, НЕ фильтр
   списка; серверного фильтра `specialist=` нет — отбор по специалисту UI
   делает клиентски по items; `by=` фильтрует источник запуска
   (manual/automation). Таймстемпы всех фаз отдавать как есть.
6. Пороги reaper (10/30 мин) — в документации или meta-эндпоинте: UI-отсчёты
   не хардкодят.
7. Единообразное поле `actor` (declared identity) во всех событиях исполнения
   (включая закрываемый gap `kind:"report"`).
8. Резерв north-star: `GET /api/executors/{id}/assignments` — можно отложить,
   схема не должна делать это невозможным.
9. После reconnect — re-fetch assignments + executors (SSE — уведомление).
