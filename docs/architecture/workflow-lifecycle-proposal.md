## 1. Резюме

Предлагается расширить жизненный цикл задачи двумя колонками слева:
**backlog** (сырые идеи) и **validating** (буфер валидации с 24-часовым
таймаутом). Итоговая линейка:

```
backlog → validating → open → in-progress → blocked → resolved → done
```

Ключевые решения:

1. **Валидация — это этап, а не статус.** В mnemos state machine колонки
   `validating` не существует и вводить её там не нужно: обе новые колонки
   борда отображаются на открытый статус mnemos `open` + маркер-тег
   (`task:stage:backlog` / `task:stage:validating`). Сервер mnemos не
   меняется вообще.
2. **24ч-таймаут обслуживает фоновый свип внутри самого борда** — второй
   asyncio-цикл в FastAPI lifespan по образцу существующего
   `_profile_cache_refresher` (`server/app.py:87–93`). Инфраструктура не
   добавляется.
3. **Борд начинает зеркалировать серверные правила переходов mnemos.**
   Сегодня `move_task` пропускает любой переход (`server/store.py:272–289`
   проверяет только валидность колонки) — это расхождение с mnemos
   закрывается в той же фазе.
4. **Критическое ограничение миграции:** `_migrate()` стирает все задачи
   при смене `SEED_VERSION` (`server/store.py:166–175`). Расширение схемы
   обязано идти table-rebuild-ом с сохранением строк, без bump-а версии
   сида — иначе миграция уничтожит существующие 40+ задач.

## 2. Контекст и модель владельца

Формулировка владельца (WF-1):

> Сырые идеи (бэклог) → буфер валидации (24ч у владельца; иначе авто-архком
> на уточнение необходимости, или TL-валидация; провалидированное → авто в
> «открытые») → открытые → в работе.
>
> Правило авто-архкома: невалидированное за 24ч → archcom-уточнение или
> TL-валидация; TL-валидация → авто-постановка в работу.

Разбор на механику:

| Элемент модели | Механика в этом предложении |
| --- | --- |
| Сырая идея | задача в колонке `backlog` (без часов) |
| Буфер валидации 24ч | колонка `validating`; часы стартуют при входе в колонку |
| Провалидировано владельцем | ручной переход `validating → open` |
| Не провалидировано за 24ч | автоматика переводит в archcom-ветку (§4) |
| TL-валидация | TL подтверждает необходимость → автоматика ставит в `in-progress` |
| Открытые / в работе | существующие колонки `open` / `in-progress` без изменений |

**G2-поиск (mnemos, 2026-09-16).** Гибридный FTS+векторный поиск по
проектам `mnemos` и `mnemos-eyes` (темы: workflow state machine,
task:queue, graduation, backlog validation) готового решения не нашёл —
единственный релевантный артефакт: `task-queue-mnemos-128` в проекте
`mnemos` (open-question, тег `task:queue`, владелец
`gcw-senior-system-engineer`). Переизобретать нечего: пропозал зелёнопольный,
инвариант «таски трекера = mnemos-записи с тегом `task:queue`» подтверждён
и закладывается в основу маппинга (§5).

## 3. Модель колонок

| # | Колонка | Смысл | Часы | Кто наполняет |
| --- | --- | --- | --- | --- |
| 1 | `backlog` | сырая идея, до валидации | нет | владелец, агенты-харнесы |
| 2 | `validating` | буфер валидации | **24ч** | владелец/TL (промоция из backlog) |
| 3 | `open` | провалидирована, ждёт исполнителя | нет | авто (валидация) |
| 4 | `in-progress` | в работе | нет | TL/агент |
| 5 | `blocked` | заблокирована | нет | исполнитель |
| 6 | `resolved` | работа завершена, ждёт приёмки | нет | исполнитель |
| 7 | `done` | принята | нет | TL/владелец |

Архив остаётся **флагом** (`archived`, `server/store.py:574–601`),
ортогональным колонке, — как сегодня. Колонки `withdrawn` на борде не
появляется: отмена — это терминальный статус mnemos, см. §7 (архив vs
withdrawn).

API-контракт: `GET /api/board` отдаёт `columns` списком, клиент рендерит
колонки из ответа (`web/js/app.js:199`), поэтому добавление двух значений —
аддитивное изменение; SSE-словарь расширяется новыми `kind` (§6), что
разрешено правилами эволюции (`ui-contract.md` §11, additive-only).

## 4. Правила валидации и переходов

### 4.1 Жизненный цикл валидации

1. **Создание.** Новая идея попадает в `backlog` (значение по умолчанию
   `col=backlog` в `POST /api/tasks`). Часов нет.
2. **Промоция в валидацию.** Владелец или TL переводит идею в
   `validating` — сервер фиксирует `stage_since = now` (новая колонка
   схемы, см. §8). С этого момента идёт 24ч-окно.
3. **Исход A — владелец провалидировал** (в пределах окна): ручной переход
   `validating → open`. Часы снимаются.
4. **Исход B — таймаут 24ч:** фоновый свип переводит задачу в
   archcom-ветку: остаётся в `validating`, но получает тег
   `task:stage:archcom-review`, уведомление (category `work`) и событие
   `task.validation-timeout`. Идея ждёт уточнения необходимости архкомом.
5. **Исход C — TL-валидация:** TL подтверждает необходимость в любой
   момент ветки B (или напрямую из окна A) → автоматика ставит задачу в
   `in-progress` с тегом `validated-by:tl` и уведомлением.
   Переход `open → in-progress` разрешён серверной машиной mnemos
   (`src/vesmaro/workflow.py:74`), авто-постановка ей не противоречит.

### 4.2 Матрица прав (кто может что)

| Действие | Владелец | TL | Агент-харнес | Автоматика |
| --- | :-: | :-: | :-: | :-: |
| Создать идею (`→ backlog`) | да | да | да | — |
| Промоция `backlog → validating` | да | да | нет | — |
| Валидация `validating → open` | да | да | нет | — |
| TL-валидация `→ in-progress` | да | да | нет | — |
| Таймаут-перевод в archcom-ветку | — | — | — | да (24ч) |
| `in-progress ↔ blocked` | да | да | да (свои задачи) | — |
| `→ resolved` | да | да | да (свои задачи) | — |
| `resolved → done` (приёмка) | да | да | нет | — |
| Архивирование | да | да | нет | — |
| Отмена (withdrawn, confirm) | да | да | нет | — |

### 4.3 Правила переходов на борде (зеркало mnemos)

Серверная машина mnemos (`mnemos/src/vesmaro/workflow.py:73–84`,
проверяется сервером, аудит-лог, локи):

```
open        → in-progress | withdrawn          (open → blocked ЗАПРЕЩЁН)
in-progress → blocked | done | withdrawn
blocked     → resolved | withdrawn             (blocked → done ЗАПРЕЩЁН)
resolved    → in-progress | done | withdrawn
done, withdrawn → терминальные
```

Бордовое зеркало = `ALLOWED_TRANSITIONS` + преп-этапы:

| С блока | Разрешённые переходы | Комментарий |
| --- | --- | --- |
| `backlog` | `validating`, `withdrawn` | идея отменяется до валидации |
| `validating` | `open`, `in-progress` (TL-валидация), `backlog` (возврат), `withdrawn` | |
| `open` | `in-progress`, `validating` (возврат на доработку), `withdrawn` | **`open → blocked` запрещён** — как в mnemos |
| `in-progress` | `blocked`, `resolved`*, `withdrawn` | `→ done` напрямую запрещён (зеркало `blocked→done`-правила: приёмка через `resolved`) |
| `blocked` | `in-progress` (blocker снят), `withdrawn` | вместо mnemos-ребра `blocked → resolved` — возврат в работу; `blocked → done` запрещён |
| `resolved` | `done`, `in-progress` (доработка), `withdrawn` | |
| `done`, `withdrawn` | — | терминальные |

Расхождение с mnemos в одной точке: mnemos имеет ребро
`blocked → resolved`, зеркало ведёт `blocked → in-progress → resolved`.
Это осознанный выбор: «resolved» на борде означает «работа завершена,
ждёт приёмки», а снятие блокировки лишь возвращает работу. mnemos-статус
при этом остаётся `blocked` → `in-progress` → `resolved` — расхождения в
маппинге нет (ребро `blocked → in-progress` в mnemos отсутствует, но
`in-progress` достижим через `resolved`; финальный консенсус — открытый
вопрос №3, §9).

Запрещённые переходы `move_task` отклоняет с `409` и подсказкой
(«blocked → done запрещён: сначала resolved»).

## 5. Маппинг на mnemos state machine

Инвариант: каждая задача борда — mnemos-запись с тегом `task:queue`;
`workflow`-статус записи управляется серверной машиной mnemos (переходы,
аудит-лог, локи — на стороне mnemos, борд их не дублирует, а соблюдает).

| Колонка борда | mnemos workflow | Маркер-тег записи | Кто двигает mnemos |
| --- | --- | --- | --- |
| `backlog` | `open` | `task:queue`, `task:stage:backlog` | борд-сервер при создании |
| `validating` | `open` | `task:queue`, `task:stage:validating` | борд-сервер |
| `validating` + archcom-ветка | `open` | + `task:stage:archcom-review` | борд-сервер (свип) |
| `open` | `open` | `task:queue` (стейдж-тег снят) | борд-сервер |
| `in-progress` | `in-progress` | `task:queue` | борд-сервер / агент |
| `blocked` | `blocked` | `task:queue` | борд-сервер / агент |
| `resolved` | `resolved` | `task:queue` | борд-сервер |
| `done` | `done` | `task:queue` → knowledge-тег (graduation) | борд-сервер |
| отменена (confirm) | `withdrawn` | — | борд-сервер (явное действие) |

Graduation: `done`-задача не удаляется, а «выпускается» в память — тег
`task:queue` снимается/заменяется на knowledge-тег, содержание записи
остаётся знанием проекта. Статус `done` — терминальный, это согласуется с
необратимостью выпуска.

### 5.1 Ключевой trade-off отображения `validating`

**Выбрано: `validating → mnemos open + маркер-тег`** (вариант «гибрид»
выброшен — см. ниже).

Плюсы:

- сервер mnemos не меняется вообще — ноль миграций в независимом продукте
  со своим релизным циклом; mnemos-статус `open` честен: работа над
  записью ещё не начата;
- аудит переходов pre-validation (кто промоted, когда истекло окно)
  живёт в штатном audit-логе mnemos workflow (`workflow history`);
- одна семантика для всех читателей памяти: запись со статусом `open`
  и тегом `task:stage:*` однозначно читается как «идея до валидации».

Минусы (принимаются осознанно):

- **статус mnemos не различает backlog / validating / open** — различие
  живёт только в теге; любой потребитель, фильтрующий по
  `workflow=open`, получит и сырые идеи. Митигация: канонический фильтр
  «задачи к работе» = `task:queue` БЕЗ `task:stage:*`;
- рассинхрон тега при недоступности mnemos: борд пишет колонку в SQLite
  локально, тег-синк откладывается до следующего свипа (eventual
  consistency, границы — §6.3).

Отвергнутый гибрид: идеи в `backlog`/`validating` живут только в SQLite
борда, mnemos-запись создаётся при выпуске в `open`. Минусы перевешивают:
ломается инвариант «таски трекера = mnemos-записи с `task:queue`»,
pre-validation история выпадает из audit-лога mnemos, а «тихие» идеи
(не дошедшие до валидации) теряются для памяти проекта — ровно те, чья
судьба («почему идея умерла») и есть знание.

## 6. Автоматика 24ч-таймаута

### 6.1 Варианты

| Вариант | Суть | Плюсы | Минусы |
| --- | --- | --- | --- |
| A. In-process свип борда | второй asyncio-цикл в FastAPI lifespan | нулевая инфраструктура; прямой доступ к store, mnemos-клиенту, SSE, notifications; паттерн уже есть (`server/app.py:87–93,144–145`) | живёт в процессе борда; при даунтайме свип стоит |
| B. Cron хоста / systemd timer | внешний планировщик дёргает `POST /api/maintenance/validation-sweep` | независим от рестартов борда | новая инфра-единица; нужен авторизованный admin-endpoint; логика в двух местах |
| C. Сторона mnemos | processor/pipeline mnemos проверяет теги | — | mnemos не знает семантику борда — неверный слой; отвергнуто |

### 6.2 Рекомендация: вариант A

Фоновый цикл `_validation_sweep` (интервал 5 мин, exception-guard, как у
рефрешера профилей):

1. выбрать задачи `col IN ('validating')`, тег archcom-ветки не стоит,
   `now - stage_since > 24h`;
2. переключить в archcom-ветку (тег + notification `work` + SSE
   `task.validation-timeout`);
3. синхронизировать маркер-тег в mnemos (неудача — не ошибка свипа,
   ретрай на следующем проходе).

Часы привязаны к `stage_since` (новая колонка схемы, проставляется при
каждой смене колонки), а не к тикам — поэтому **restart-safe**: после
падения и подъёма свип досматривает просроченные задачи, двойной
обработки нет (сам перевод в archcom-ветку и есть guard).

### 6.3 Честные границы

- **Один воркер.** Контейнер поднимает `uvicorn` без `--workers`
  (`Containerfile:30`) — in-process свип однократен. Если когда-нибудь
  появятся >1 воркеров, потребуется распределённый лок (advisory lock
  SQLite или выборка `UPDATE ... WHERE stage_since=?` по оптимистичной
  блокировке). Сегодня — не нужно, зафиксировано как условие.
- **Латентность.** «24ч» фактически 24ч…24ч05м (интервал свипа). Для
  человеческого буфера валидации это несущественно.
- **Даунтайм борда** продлевает окно: часы идут по wall-clock
  (`stage_since`), свип после простоя догоняет всё просроченное разом.
- **mnemos недоступен** — колонка двигается в SQLite, тег-синк откладывается;
  каноничное состояние = колонка борда, mnemos догоняет. Это уже текущая
  модель борда (тонкая проекция над двумя источниками, `store.py:1–12`).

## 7. Риски и edge-cases

| # | Риск / кейс | Последствие | Митигация |
| --- | --- | --- | --- |
| 1 | **Freeze rule (ADR 0006):** борд feature-frozen, новые фичи → L1 | UI-фаза — фича на замороженном борде | Серверная модель + автоматика = long-lived asset (ADR 0006 §4, «transfers to L1») — разрешены; UI-фаза оформляется записью в freeze-exception register (class, rationale, TL triage) либо едет в L1 |
| 2 | **`SEED_VERSION` wipe** (`store.py:166–175`): bump версии сида стирает все задачи | миграция уничтожает 40+ задач | Миграция схемы — table-rebuild в `_migrate()` с сохранением строк; SEED_VERSION не трогать; dry-run на копии board.db обязателен |
| 3 | **CHECK-констрейнт** `col` (`store.py:39`): SQLite не умеет ALTER CHECK | новые значения не вставятся | Table-rebuild (новая таблица → копия → drop → rename) внутри `_migrate()` |
| 4 | **`blocked → done` на борде** сегодня разрешён (`move_task` не проверяет переходы) | расхождение с mnemos; после зеркалирования часть привычных действий начнёт отклоняться (409) | Зеркало переходов вводится в той же фазе; 409 несёт подсказку «через resolved»; в отчёте миграции — список задач с «невозможной» историей |
| 5 | **`open → blocked` запрещён в mnemos** (`workflow.py:62–65`), борд сегодня разрешает | существующие blocked-задачи, миновавшие in-progress, невоспроизводимы в mnemos-зеркале | Нормализация при миграции данных (§8, шаг 4): такие задачи получают поправленную историю (in-progress → blocked) или фиксируется diverged-статус |
| 6 | **Архив vs withdrawn:** withdrawn — терминальный; unarchive невозможен | если архив двигает mnemos в withdrawn, разархивирование ломается | Архив — только бордовский флаг, mnemos-статус не трогает; withdrawn — отдельное явное действие «отменить» с confirm (необратимо) |
| 7 | **TL-авто-постановка в работу** обходит owner-очередь приоритизации | задача встаёт в in-progress без явного приоритета владельца | Тег `validated-by:tl` + notification; открытый вопрос №2 (нужен ли assignee) |
| 8 | **Захламление backlog** идеями от агентов | шум, разросшаяся колонка | Лимит не вводится в v0; метрика ретро (§8, шаг 5); при необходимости — квоты на агента |
| 9 | **SSE gap** `task.archived/unarchived` клиентом не обрабатывается (`ui-contract.md` §11) | доска не обновится по тем же причинам для новых kinds | Клиент обязан молча игнорировать неизвестные kinds (уже делает); `refreshBoard()` для новых событий — в UI-фазе |
| 10 | **Свип и человеческий фактор:** владелец в отпуске | все идеи уезжают в archcom-ветку пачкой | Это и есть задуманное поведение (авто-эскалация); пачка обрабатывается одной сессией архкома |

## 8. План миграции (future — выполняется только после утверждения)

Шаг 0. **Утверждение.** Владелец принимает/правит этот документ; все
«открытые вопросы» (§9) закрыты. Этот документ после утверждения получает
ADR-номер (кандидат: 0009).

Шаг 1. **mnemos.** Изменений нет. Проверить только наличие тегов
`task:stage:*` в tag-валидаторе mnemos (`mnemos tags`), добавить при
необходимости.

Шаг 2. **Сервер борда** (одна фаза, один PR):

- `_migrate()`: table-rebuild `tasks` — расширить CHECK `col`
  (+`backlog`, `+validating`), добавить колонку `stage_since TEXT`;
  **без bump-а `SEED_VERSION`** (риск №2);
- transition guard в `move_task` (матрица §4.3), 409 с подсказкой;
- `_validation_sweep` в lifespan (§6.2);
- SSE: `task.validated`, `task.validation-timeout` (additive-only,
  `ui-contract.md` §11);
- `POST /api/tasks`: значение по умолчанию `col=backlog`.

Шаг 3. **UI** (отдельный PR, freeze-exception register):

- рендер двух колонок (клиент уже читает `board.columns`,
  `app.js:199`) + стили, ctx-menu, кнопка «Валидировать»;
- обработка новых kinds в `refreshBoard()`.

Шаг 4. **Данные** (скрипт, dry-run сначала):

- grandfathering: существующие колонки переносятся 1:1
  (`open→open`, `in-progress→in-progress`, …); `backlog`/`validating`
  стартуют пустыми — все текущие задачи считаются провалидированными;
- нормализация риска №5 (blocked без in-progress в истории);
- бэкфилл: для задач без mnemos-записи — создать (`task:queue` +
  workflow `set` до соответствующего статуса); сверить статусы
  mnemos ↔ колонка, отчёт расхождений.

Шаг 5. **Ретро через 2 недели:** метрики — среднее время в `validating`,
доля исходов A/B/C, размер `backlog`; решение о вторичном таймауте
archcom-ветки (вопрос №2).

## 9. Открытые вопросы (к владельцу, вместе с утверждением)

1. **Точка старта часов.** Создание сразу в `validating` (часы с момента
   создания) или ручная промоция `backlog → validating`?
   Рекомендация: ручная промоция — backlog остаётся парковкой без дедлайна.
2. **TL-валидация и assignee.** Требуется ли исполнитель для
   авто-постановки в `in-progress`? Рекомендация: да, без assignee
   TL-валидация останавливается на `open`.
3. **Ребро `blocked → in-progress` на борде** против mnemos-ребра
   `blocked → resolved` (§4.3). Принять расхождение (рекомендация) или
   ввести бордовую колонку-смысл «resolved = снята блокировка» — тогда
   приёмочная колонка переименовывается. Рекомендация: принять расхождение,
   семантику `resolved = ждёт приёмки` не менять.
4. **Вторичный таймаут archcom-ветки:** авто-withdraw через N дней или
   бессрочно? Рекомендация: 7 дней — повторное уведомление, 30 дней —
   кандидат на withdrawn по ручному решению.
