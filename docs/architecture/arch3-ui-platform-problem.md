## 1. Контекст и текущее состояние (факты из репо)

### 1.1 Два фронтенда и их реальное состояние

| | vanilla-борд (`web/`) | L1 viewer (`viewer/`) |
| --- | --- | --- |
| Стек | no-build ES modules, один `app.js` | Vite + React 18 + TS (strict) + Router 7 + TanStack Query + shadcn/ui |
| Статус | прод (кластер, v1.3.2), 6 раундов одобрения v0.3–v0.9, **feature-frozen** (ADR 0006) | рабочий каркас: 7 роутов (`App.tsx`), шлюз с 3 адаптерами (Mock/Http/Tauri, ADR 0002), auth-флоу c TOTP-challenge стейт-машиной, a11y-компоненты, vitest, openapi-codegen со schema-drift guard |
| Data plane | **борд-merge API** своего сервера (`/api/tasks`, `/api/memories/*`, SSE `/api/events`) | **прямое подключение к одному mnemos** (`HttpAdapter`: `/search`, `/memories`, `/tags`, `/recall/agent/*`, `/auth/*`; снапшот = OpenAPI mnemos 4.1.0) |
| В образе | да (`Containerfile` копирует `web/`) | **нет** — `dist/` в контейнер не попадает |
| URL | `https://vesmaro.abyss.lab/` (ingress path `/` Prefix → board service) | нигде не развёрнут |

Ключевой факт: **каркас viewer готов, но его data plane — wire-контракт mnemos,
а не merge-API борда.** `adapterConfig.ts` дефолтит на same-origin `/api`, но
борд-сервер на этих путях отдаёт свою модель (multi-store merge, `per_server`
provenance), не mnemos-словарь. Конвергенция ≠ «переложить борд в React» —
она требует BoardAdapter в шлюзе (см. §3.3).

### 1.2 Платформенные механизмы борд-сервера

- **Auth-мутаций:** fail-closed bearer `VESMARO_BOARD_TOKEN` — пустой токен →
  503 на любую мутацию, несовпадение → 401, constant-time
  (`server/app.py:1768–1784`). Токен один на всех писателей; ADR 0009 (на
  ратификации) разводит ui/machine-токены. **Чтения — открыты** (за ingress TLS).
- **mnemos-токены:** борд ходит в хранилища с `mnk_`-токенами через
  `token_ref` (env/file, SEC-2), TOTP-флаг на стороне mnemos
  (`totp_required=0` в текущем контуре, `values.yaml`); viewer умеет
  mnk_-логин + TOTP-challenge (`gateway/auth.ts`).
- **SSE** `/api/events` (`app.py:1788–1813`): in-process fan-out, at-most-once,
  без resumption; словарь additive-only, версионирован (`ui-contract` §11).
- **OpenAPI + контракт-тесты:** FastAPI отдаёт честную схему,
  `tests/test_openapi_contract.py` пинит её — API-first уже не лозунг, а
  механизм (гейт 1→2 АРХКОМ-1 закрыт этим же).
- **Rate limiters** как устоявшийся паттерн: reflect/draft/report/inbox
  (`app.py:1152,1222,1373,1429`), in-memory sliding window (`security.py:235`).
- **Маскирование секретов:** `mnk_*` и `Bearer …` скрабятся в логах
  (`security.py:219–231`) — паттерн расширить на новый класс токенов.
- **Egress-политика** для хранилищ (SEC-1, `VESMARO_ALLOWED_MEMORY_HOSTS`),
  NetworkPolicy default-deny, ingress только от traefik.

### 1.3 TLS сегодня

Self-signed секрет `vesmaro-eyes-tls` для `vesmaro.abyss.lab`
(`values.yaml`, «browser warning is accepted», `scripts/gen-tls-secret.sh`).
Это напрямую ограничивает и QR-пейринг, и PWA (§4.5, §5.2).

### 1.4 Референс: как устроен QR-пейринг в zcode (Web Remote Control)

Исследовано по установленному бандлу zcode 3.14.0
(`/opt/ZCode/resources/glm/zcode.cjs` — только идентификаторы и структуры,
без значений секретов) и структуре `~/.zcode` / `~/.config/ZCode`.

- **Модель:** desktop-приложение (управляемая сторона) отдаёт удалённому
  веб/мобильному клиенту управление сессией. IPC-команды:
  `zcode:start/stop-web-remote-control`, `zcode:reset-web-remote-control-pairing`,
  `zcode:get-web-remote-control-status`, событие `…-status-changed`.
- **QR = URL веб-приложения + параметры:** `buildWebRemoteControlExternalQrUrl`
  кладёт в query: `sid` (deviceSid — идентификатор desktop-сессии), `hash`
  (passHash — производная от пейринг-секрета, не сам секрет), `t` (timestamp,
  защита от устаревших QR), опционально `mid`, `name`, `app_version`,
  `theme`. Телефон открывает URL → попадает в хостимое облаком веб-приложение.
- **Транспорт — облачный relay:** desktop подключается **исходящим**
  WebSocket к `wss://…/ws` (relay-URL), мобильный клиент — туда же; RPC гонится
  конвертами (json/bytes) через relay. Нужен потому, что desktop сидит за NAT.
- **Рукопожатие пейринга:** роли `device` / `terminal`; объект
  `{passHash, nonce, role, deviceSid, proof}` — обе стороны доказывают знание
  общего секрета разными proof над одним nonce (PAKE-подобная схема), т.е.
  QR (содержащий hash) сам по себе токеном не является — полный доступ даёт
  только proof-обмен.
- **Таксономия отказов** (WebSocket close codes): 4004 SessionNotFound,
  4009 SessionConflict, 4010 DesktopDisconnected, 4011 SessionExpired,
  4012 WorkspaceClosed, 4013 InvalidMobileConnection.
- **Живость:** heartbeat 120 с + jitter 5 с, reconnect с jitter, recovery-timeout.
- **Персистентность пейринга:** связка запоминается, есть отдельная команда
  reset (разрыв всех доверенных устройств).
- Прочее: OS-level deep-link схема `zcode://`; локальная собственная CA
  (`~/.zcode/v2/certs/zcode-network-ca.{pem,key}` — имена).

**Отличие нашей топологии:** у zcode управляемая сторона — desktop за NAT,
поэтому relay в облаке. У нас управляемая сторона — **борд-сервер за ingress
в LAN** (`vesmaro.abyss.lab`), устройство в том же контуре достигает его
напрямую. Облачный relay нам не нужен (и был бы шагом назад по приватности:
трафик памяти через третьи руки).

## 2. Проблемы

| # | Проблема | Факт сегодня |
| --- | --- | --- |
| П1 | **Нет целевой платформы интерфейса.** «Веб-утилита» не имеет ответа «куда кладывается новый домен»: борд заморожен, viewer не развёрнут и говорит на чужом wire-контракте | все фичи → «L1 backlog» (ADR 0006), но L1 как поверхность не существует в проде |
| П2 | **Нет способа подключить устройство.** Единственный путь: знать URL, принять self-signed warning, вручную вставить токен (mnk_ в viewer / bearer в curl) | понятия device-сессии в системе нет; reads открыты — «подключение» сегодня = просто открыть URL |
| П3 | **Путь к приложениям не спроектирован.** ADR 0001 (web-first, Tauri later) писался до появления борд-сервера; контрактные требования мобильного клиента (пагинация, ETag, resumption SSE, device-auth) не зафиксированы | пагинация непоследовательна: archive — `limit/offset/total` (`app.py:1305–1341`), notifications — курсор `after_id`, pulse/search — только capped `limit` без продолжения, `GET /api/tasks/inbox` — вообще без пагинации (`app.py:1433`); SSE без resumption |
| П4 | **Сервер и деплой заточены под один SPA.** Один static-root (`web/`), один ingress-path, один токен писателя | `app.mount("/", StaticFiles(...))`, `Containerfile` копирует только `web/` |

Корневая формулировка: платформа интерфейса описана как «судьба двух
фронтендов» (ADR 0006), но владелец уже перешёл на следующий уровень абстракции —
**«интерфейс = приложение над сервером памяти»**. ADR 0006 отвечал, *когда*
мигрировать; теперь нужен ответ, *на чём строить* и *как подключать клиентов*.

## 3. Вопрос 1 — Платформа интерфейса: конвергенция или эволюция обоих

### 3.1 Целевая картина

«Полноценная веб-утилита» = **одно приложение**: shell (роутер, навигация,
дизайн-система, auth, пейринг, PWA-обвязка) + домены-страницы
(search, memories/pulse, tasks/канбан, inbox, reports, specialists, status, …).
Раскладку страниц и навигацию даёт дизайн-концепт; платформа даёт: роуты,
доменные модули `features/*` (уже такая структура), шлюз, auth, деплой-слот.

### 3.2 Варианты

**A. Конвергенция в одно React-приложение** (viewer = каркас; борд-функции
переезжают страницами; vanilla-борд доживает как замороженный кокпит до гейта).

- **За:** (1) каркас уже оплачен и не игрушечный — роутер с lazy-чанками,
  шлюз с тремя адаптерами и тестами, auth-стейт-машина с TOTP, дизайн-система
  на токенах, codegen-дисциплина; (2) **каждая платформенная способность
  строится один раз** — QR-пейринг, PWA, offline-кеш, deep links, пуш — иначе
  при эволюции обоих каждая строится дважды (или углубляет дивергенцию);
  (3) ADR 0006 уже маршрутизирует все фичи в L1 — конвергенция лишь называет
  конечное состояние, не меняя текущих правил; (4) переносимое ядро
  (merge-API, SSE-словарь, онтология, токены) уже контрактно запинено —
  OpenAPI + контракт-тесты, регрессионный риск канбана ограничен контрактом,
  а не кодом.
- **Против:** канбан переписывается (6 раундов одобрения — риск потери
  поведения; митигируется: канбан мигрирует **последним**, parity-чеклист TL,
  раунд фидбека владельца на приёмку, борд остаётся в проде до переключения);
  DOM/JS борда не переносится (CHARTER §8 — уже принятое правило, не новая
  цена); в сборку образа приходит Node-стейдж.

**B. Эволюция обоих** (борд — по freeze-исключениям, viewer — параллельно).

- **За:** ноль миграционного риска; kanban-регрессии исключены.
- **Против:** вечные два стека; каждое платформенное требование владельца
  (пейринг, PWA, вкладки) — дилемма «freeze-исключение или ждать L1»;
  бюджет реестра исключений (≤2, АРХКОМ-2) исчерпается первыми же
  платформенными запросами; токен-модель и auth-UX придётся поддерживать в
  двух клиентах.

**C. Статус-кво ADR 0006** (решение отложено до конвергенционного гейта).

- Устранено стимулом: гейт ADR 0006 отвечает «когда переносить канбан», но не
  «где строить всё остальное». Пока C не разрешён, П1 остаётся открытой.

### 3.3 Честные сложности конвергенции (что надо сделать, а не только решить)

1. **BoardAdapter в шлюзе.** Viewer говорит на wire-контракте mnemos;
   merge-API борда — другой словарь (`/api/memories/pulse` c `per_server`,
   `/api/tasks`, `/api/events`). Нужен адаптер `BoardAdapter implements
   MemoryGateway` (+расширения: SSE, tasks) — это же гейт 2→3 АРХКОМ-1
   («L1 потребляет /api/memories/*»). ADR 0007 запрещает L1 собственный
   multi-probe — конвергенция идёт **только** через борд-сервер, что и делает
   BoardAdapter единственной точкой.
2. **Auth-двухконтурность.** В одном приложении живут: mnk_-логин в mnemos
   (сегодняшний viewer) и ui-token борда (мутации, ADR 0009). После
   конвергенции mnk_ из UI уходит (борд сам держит token_ref хранилищ);
   фронт аутентифицируется только у борд-сервера. Это упрощение, но его
   надо спроектировать (см. §4.4).
3. **Static/маршрутизация двух SPA в одном контейнере** (§6).

### 3.4 Рекомендация и план перехода (strangler, канбан последним)

**Конвергенция в одно React-приложение; freeze-правило ADR 0006 сохраняется
до последней фазы.** Новые домены с первого дня живут в React-приложении;
канбан мигрирует последним, под конвергенционный гейт.

| Фаза | Содержание | Гейт/выход |
| --- | --- | --- |
| Ф0 — фундамент | viewer собирается в образ и разворачивается на `/app` (§6); BoardAdapter в шлюзе (read-пути: pulse, search, memories, tags); приложение ходит на same-origin `/api` | контракт-тесты BoardAdapter зелёные; владелец видит `/app` рядом с бордом |
| Ф1 — новые домены | все новые поверхности (входящие, отчёты, пульс как страница, панели из дизайн-концепта) — страницы/вкладки React-приложения; реестр freeze-исключений борда = 0 | первый домен принят владельцем |
| Ф2 — parity (чтение) | daily-loop по чеклисту ADR 0006: пульс, поиск, drill задачи — read-only; канбан-вью только чтение | parity-чеклист (TL) закрыт по read-части |
| Ф3 — parity (действия) | мутации: перемещения, редактирование, assignment-триггер (ADR 0009) на ui-token; канбан-доска с drag&drop в React | раунд фидбека владельца = гейт (b) ADR 0006 |
| Ф4 — переключение | `/` → React-приложение; старый борд доступен `/board` одно deprecation-окно (bug-fix only), затем вывод; ADR 0006 закрывается | владелец подписывает переключение |

Гейт (a) ADR 0006 (mesh query-API, ADR 0007) не двигается: он меняет
внутренности BoardAdapter (адаптер над query-API mesh), не фазы.

## 4. Вопрос 2 — QR-пейринг устройства

### 4.1 Топология: LAN-direct вместо relay

| | **LAN-direct (наша рекомендация)** | Cloud-relay (модель zcode) |
| --- | --- | --- |
| Транспорт | устройство → ingress → борд-сервер напрямую (как любой браузер) | отдельный relay-сервис (облако или свой pod), оба клиента — исходящие WS |
| Когда нужен | сервер достижим (LAN/VPN) — наш случай | управляемая сторона за NAT (у zcode — desktop) |
| Новая инфраструктура | нет | да (relay + его доступность/безопасность) |
| Приватность | трафик не покидает контур | трафик памяти через третью сторону |
| Вывод | **берём** | отвергаем; сценарий «вне LAN» закрывает VPN, не relay |

### 4.2 Протокол (кто инициирует: всегда доверенный клиент)

Сценарий-основа: владелец хочет подключить телефон. Инициатор — **основной
(уже аутентифицированный) клиент**, не устройство. Это главное
security-решение: QR показывает доверенная сторона, устройство лишь
сканирует; подтверждение — снова на доверенной стороне (SSE-событие). Ни один
шаг не позволяет устройству получить доступ без двух действий владельца
(создать + подтвердить).

1. `POST /api/pairing` (ui-token) → `{pairing_id, code (одноразовый, 128-bit,
   TTL 5 мин), verify (4 цифры для сверки), expires_at}`. UI рисует QR:
   `https://vesmaro.abyss.lab/#/pair?t=<code>` (URL = endpoint + токен; как
   `sid/hash/t` у zcode — токен в URL, не секрет наизусть).
2. Устройство открывает URL → страница `/#/pair` шлёт
   `POST /api/pairing/exchange {code, device_name}` → пока не подтверждён:
   `202 {status:"awaiting_confirmation", verify}`. Сервер переводит pairing в
   `scanned`, эмитит SSE `pairing.requested`.
3. Основной клиент получает SSE-событие → тост/панель «запрос подключения
   <device_name>, код <verify>» → `POST /api/pairing/{id}/confirm {allow}`.
   **Сверка `verify` на обоих экранах** — защита от подменного QR (фишер
   показал жертве свой QR, владелец видит чужие цифры и жмёт «отклонить»).
4. Страница устройства повторяет exchange → `200 {device_id, device_token
   (mnd_…), scope, expires_at}`. Pairing → `issued`, гаснет.
5. Device-token живёт в хранилище устройства (PWA/приложение), шлётся как
   `Authorization: Bearer mnd_…` на те же эндпоинты.

### 4.3 Токен-модель: третий класс токенов (расширение ADR 0009)

ADR 0009 вводит ui/machine; добавляем **device** — отдельный класс с
минимальными правами:

| Класс | Кто | Права | TTL |
| --- | --- | --- | --- |
| ui | браузер владельца | полный UI-контур | сессия |
| machine | поллер/харнесы | assignments, reports | длинный, по ADR 0009 |
| **device** | спаренные устройства | v0 — **read-only** (pulse, search, memories, задачи-чтение, SSE-чтение); мутации задач (`scope:"tasks"`) — отдельным решением архкома позже; store-ops/валидация — никогда | 30 дней sliding при активности, hard-cap 90 дней |

- Лимит: **≤5 активных device-сессий**; список/ревок — `GET/DELETE
  /api/devices/{id}` из основного клиента (SSE `pairing.revoked`).
- `mnd_`-префикс добавить в `_SECRET_PATTERNS` (`security.py:219`) — маскирование
  в логах с первого дня (урок SEC-2).
- mnk_-токены и TOTP остаются **серверной** кухней борда (token_ref per store);
  устройство никогда не видит mnk_ и не проходит TOTP — его идентичность
  device-session, выданная пейрингом.

### 4.4 TLS и self-signed (критическая зависимость)

QR-пейринг мобильного устройства при self-signed сертификате упирается в
страху браузера: предупреждение на каждый профиль, PWA не устанавливается,
fetch из PWA-контекста может блокироваться. Варианты:

| Вариант | Цена | Вывод |
| --- | --- | --- |
| **lab-CA на устройство** (расширить `gen-tls-secret.sh`: CA + leaf; CA установить на телефон/десктопы владельца) | низкая; разовая ручная операция на устройство | **рекомендуется** — согласуется с пейрингом как «ритуал подключения устройства» |
| ACME/Let's Encrypt + DNS | нужен публичный домен/DNS-01; lab-домен `.abyss.lab` не подходит | фиксировать как триггер: появится внешний доступ — переходим |
| HTTP в LAN для v0 | снимает боль ценой plaintext-токенов | **отвергается** (bearer/device-токены в открытом канале) |

Решение по CA — отдельный вопрос архкому (№5, §7), потому что меняет
операционный ритуал (RUNBOOK).

### 4.5 Security-требования (pairing = атака-поверхность)

1. **Инициация и подтверждение — только ui-token** (fail-closed: pairing
   эндпоинты 503 без настроенного ui-токена — по образцу `_guard_write`).
2. **Одноразовость и TTL:** code single-use, 5 мин; повторный exchange
   использованного code → 410; brute-force: exchange 5 попыток/10 мин на
   pairing, создание 3/10 мин на клиента (паттерн RateLimiter).
3. **Анти-фишинг:** короткий `verify`-код на обоих экранах; confirm без
   совпадающего verify-контекста невозможен (код живёт в объекте pairing).
4. **Ревок в один шаг** из основного клиента; ревок всех устройств = reset
   (по образцу `reset-web-remote-control-pairing` zcode).
5. **Аудит:** запись в notifications (system) о создании/подтверждении/ревоке
   — видимость аномалий без отдельного лог-инструмента.
6. Scope device-токена пишется в токен и проверяется на каждом запросе
   (middleware перед `_guard_write`), не «на совести клиента».

## 5. Вопрос 3 — Масштабирование на приложения

### 5.1 Варианты оболочки

| | **PWA (поверх конвергентного web-app)** | Tauri 2.0 (ADR 0001 Phase 2) | Нативные (iOS/Android) |
| --- | --- | --- | --- |
| Что даёт | иконка на телефоне/десктопе, fullscreen, offline-shell позже (service worker), push позже (VAPID) | local-first: SQLite in-process, без HTTP-сервера mnemos на устройстве (ADR 0002, `TauriAdapter` — стаб) | максимум платформенных API |
| Цена | ~дни (manifest+icons); требует доверенный TLS (см. §4.4) | Rust-тулчейн, подпись, отдельный релизный цикл | двойная разработка, сторы |
| Когда | **сейчас (минимум)** | без изменений — Phase 2 по ADR 0001 | Not-doing (нет JTBD-сигнала) |
| Связь с пейрингом | device-token хранится в PWA-хранилище — пейринг и есть «установка» | не конфликтует: Tauri-приложение = тот же фронт + другой адаптер | — |

**ADR 0001 пересматривать не нужно — подтвердить.** Web-first доказан
(борд-сервер сам стал платформой); «Tauri later» не двигается: local-first —
отдельный JTBD (работа с памятью без сети), не блокирует ничего здесь.

### 5.2 Что заложить в контракты СЕЙЧАС (чтобы потом не переделывать)

1. **Пагинация везде, единообразно.** Сегодня: archive — `limit/offset/total`
   (`app.py:1305–1341`), notifications — курсор `after_id` (`app.py:1284`),
   pulse/search — capped `limit` без продолжения (`app.py:964–1005,1103–1126`),
   `GET /api/tasks/inbox` — без пагинации вовсе (`app.py:1433`). Зафиксировать:
   все списковые эндпоинты принимают `limit&cursor` (+`total` где дёшево),
   additive — старые параметры не ломаются. Мобильный список без пагинации =
   главный источник «переделать потом».
2. **ETag/If-None-Match на read-эндах** (tasks, memories, stats) — дешёвый
   кеш для мобильных и офлайн-стратегий. Additive, серверно.
3. **Device-auth (§4) в модели авторизации с первого дня** — потом вводить
   третий класс токенов дороже, чем сразу.
4. **SSE: стратегия resumption как v2-кандидат.** Мобильная сеть рвёт
   стримы; at-most-once + re-fetch достаточно и сегодня, но зафиксировать в
   `ui-contract` §11, что v2 (Last-Event-ID/персистентный журнал) —
   проектное направление, чтобы решения сегодня его не блокировали
   (например, event_id должен быть монотонным уже сейчас).
5. **Same-origin без CORS-боли:** приложение и API за одним origin
   (`/app` + `/api` на одном хосте) — CORS-заголовки не нужны вовсе; это
   надо зафиксировать как принцип, чтобы внешние клиенты не тащили
   CORS-исключения, а ходили через ingress-контур с токенами.
6. **OpenAPI-дисциплина неизменна:** новые эндпоинты (pairing, devices,
   пагинация) приходят со схемой + пин-тестом в той же фазе (урок
   `kind:"report"`-gap: контракт и код сводятся одной фазой).

- **NetworkPolicy:** без изменений — трафик устройств приходит через traefik,
  как браузерный.

## 8. Черновик контрактов (при «да» по вопросу №2)

### 8.1 Pairing lifecycle

```
created ──scan──▶ scanned ──confirm──▶ confirmed ──exchange──▶ issued
   │                 │                                        │
   └── TTL 5 мин ────┴──────────▶ expired ◀── TTL ────────────┘
   любой шаг до issued: revoke (владелец) ─▶ revoked
```

`PairingRequest`: `id`, `code_hash` (сам code не хранится открыто), `verify`
(4 цифры), `state` (`created|scanned|confirmed|issued|expired|revoked`),
`scope` (v0: `read`), `created_by` (ui-identity), `device_name?`,
`created_at`, `scanned_at?`, `confirmed_at?`, `expires_at`.
События переходов эмитятся в SSE (§8.3) и дублируются notification-ами
(system) — аудит без нового инструмента.

### 8.2 REST-эндпоинты

| Метод и путь | Auth | Семантика |
| --- | --- | --- |
| `POST /api/pairing` `{device_name?}` | ui-token | создать; rate 3/10 мин на клиента; 201 + `{pairing_id, code, verify, expires_at}` |
| `POST /api/pairing/exchange` `{code, device_name}` | нет (rate 5/10 мин на pairing) | не подтверждён → `202 awaiting_confirmation` (+verify); подтверждён → `200 {device_id, device_token: mnd_…, scope, expires_at}`; невалиден/истёк → 404/410 |
| `POST /api/pairing/{id}/confirm` `{allow: bool}` | ui-token | scanned → confirmed / revoke; rate 3/10 мин |
| `DELETE /api/pairing/{id}` | ui-token | cancel/ревок до issued |
| `GET /api/devices` | ui-token | список device-сессий (без токенов) |
| `DELETE /api/devices/{id}` | ui-token | ревок; SSE `pairing.revoked` |

`DeviceSession`: `id`, `name`, `scope`, `created_at`, `last_seen_at`,
`expires_at` (30 д sliding, hard 90 д), `state` (`active|expired|revoked`).
Токен — hash-only в БД, префикс `mnd_`, маскируется в логах.

### 8.3 SSE-события (additive-only, зарезервировать вместе с эмиттерами)

| kind | Payload | Эмиттер |
| --- | --- | --- |
| `pairing.requested` | `pairing_id, device_name?, verify` + `notification` | exchange при `created→scanned` |
| `pairing.confirmed` | `pairing_id, device_name?` | confirm |
| `pairing.revoked` | `pairing_id \| device_id` + `notification` | revoke/ревок устройства |
| `pairing.expired` | `pairing_id` | TTL-sweep (in-process, по образцу фоновых циклов `app.py:90`) |

Правила те же, что у `assignment.*` (ADR 0009 фаза 0): резервирование в
словаре `ui-contract` §11 — той же фазой, что и эмиттеры.

### 8.4 Ограничения v0 (зафиксировать сразу)

- code: 128-bit urlsafe, single-use, TTL 5 мин; verify: 4 цифры.
- ≤5 активных device-сессий; новая сверх лимита → 409 с ревоком самой старой
  по решению владельца (не молча).
- device scope v0 = read: `GET /api/tasks*`, `GET /api/memories/*`,
  `GET /api/events`, `GET /api/health`; мутации → 403 (не 401 — токен валиден,
  прав нет).
- pairing отключён (503), если ui-token не настроен — fail-closed.

## 9. Резюме рекомендаций (одной строкой на вопрос владельца)

1. **Платформа:** конвергенция в одно React-приложение (viewer = каркас),
   strangler Ф0–Ф4, канбан последним, freeze-правило ADR 0006 действует до Ф4.

   UI)», в 1.4.x серверно + UI в React-приложении; relay-модель zcode не
   нужна.
3. **Приложения:** PWA-минимум сейчас, Tauri — Phase 2 без изменений (ADR 0001
   подтвердить), нативные — Not-doing; в контракты сейчас: единая
   курсорная пагинация, ETag, device-auth, SSE-resumption как заявленное
   направление v2, принцип same-origin (без CORS).
