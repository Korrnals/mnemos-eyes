## 0. Стимул владельца (исходная постановка, дословно)

> «Говоря про дефолтного исполнителя — я в том числе имею ввиду и возможность
> выбора агента, который будет по умолчанию. Но и авто назначение — тоже
> должно иметь место (на случай, если пользователь явно его не определил)…
> И да, интересная тема с хуками и планировщиком… Тоже стоит добавить в
> интерфейс и проработать их функциональность».

Разбор. Первая половина закрыта: цепочка разрешения исполнителя (explicit →
specialist → task → project → global → авто-подбор) вычисляется на GET, гейты
Security зафиксированы (Amendment 2 §5; АРХКОМ-4, решение 4). Эта записка — про
вторую половину. Рамка домена: **роутинг отвечает «кому», автоматизация —
«когда» и «в ответ на что»**. Планировщик (time-based запуск) и хуки
(event-based реакции) — один домен автоматизации ЗАПУСКА, ортогональный
роутингу и стоящий НАД очередью поручений, а не рядом с ней. Риск
«ползучести к scheduler'у» из вердикта Senior System Engineer на АРХКОМ-4
(протокол, решение 4: автодиспетчер — T2-гейт) закрывается именно этой рамкой:
автоматизация — отдельная явная сущность со своими гейтами, а не расширение
цепочки дефолта.

## 1. Контекст: что уже живёт

### 1.1 Очередь исполнения (Ф1 ADR 0009, смержена)

- `POST /api/assignments` — **ui-token only** (`_guard_ui_write`,
  `server/app.py:2420`; роут `app.py:1868`), rate 10/60 с (`app.py:1806–1809`),
  allowlist харнесов (`Store.KNOWN_HARNESSES`, 422 на неизвестном).
- Claim — CAS `queued→claimed` в одной транзакции с переводом задачи
  `open→in-progress` (`store.py:1075`); снапшот спеки 16K + sha256
  (`SPEC_SNAPSHOT_CAP=16384`, `store.py:79`; `create_assignment` `store.py:997`).
- Инвариант **≤1 активное поручение на задачу** — 409 (`store.py:1030–1037`);
  гейт назначаемости: archived/terminal → 422 (`store.py:1021–1028`).
- Таблица `task_assignments` (`store.py:204–227`) несёт `claimed_at` /
  `heartbeat_at` с Ф1 — reaper-ready без миграций.
- Словарь `assignment.*` зарезервирован в `ui-contract.md` §11 (строки
  172–194), additive-only; пер-пульсовые SSE запрещены (Amendment 2 §7).

### 1.2 Исполнители и поллер

- Реестр `executors` — задача ARCH-9 (после мержа Ф1; обязателен до
  мульти-харнесного rollout, триггер T1). Presence — TTL 2/10 мин,
  вычисляется на чтении. Токен-лестница L0–L2 (Amendment 2 §4).
- Поллер — транспорт №1 (не модель исполнителя): systemd timer, опрос
  `?state=queued` ~10 с c jitter, heartbeat 60 с, singleton `flock`,
  recovery-sweep (ADR 0009 §4). Фаза 2 — в ветке `feat/ab-phase2-poller`.

### 1.3 Автоматика, которая уже есть (и невидима)

| Механизм | Где | Статус |
| --- | --- | --- |
| Рефрешер профилей (цикл lifespan, 300 с, exception-guard) | `app.py:128` | живёт |
| Инбокс-сканер AGG-1 (фоновый цикл, 5 мин) | `app.py:208` | живёт |
| Валидационный свип WF-1 (24 ч, wall-clock по `stage_since`) | WF-1 §6.2 | на утверждении |

Паттерн един: in-process asyncio-цикл в lifespan, single-worker
(`Containerfile:30`), wall-clock-часы в колонках — restart-safe.

### 1.4 События и UI-каркас

- SSE `/api/events` — in-process fan-out, at-most-once; источники: роуты
  борда. Потребители — только клиенты; **борд сам на события не реагирует**.
- UI: домен «Система» концепта (`/system/{notifications,devices,settings}`,
  §2.1 концепта) — место раздела автоматизации; `/system/settings` уже
  резервирует «Исполнение» (дефолт+fallback, спека «Агенты» §2.3, §5.4).
  Волны конвергенции Ф0–Ф4 (ADR 0011); мутации/ui-token — Ф3; борд `web/`
  заморожен (ADR 0006).

## 2. Проблемы (по стимулу)

| # | Проблема | Факт сегодня |
| --- | --- | --- |
| П1 | **Нет запуска по времени.** Ни один контракт не выражает «запусти X в 07:00 / каждые N»; единственный cron в системе — таймер поллера, борду невидимый | сущности schedule нет |
| П2 | **Нет реакций на события.** События есть (`assignment.*`, `task.*`, `executor.*`), но эмиттеры — роуты, а «если assignment.failed → перезапустить/уведомить» выразить негде | сущности hook/rule нет |
| П3 | **Владелец — единственный триггер запуска.** `POST /api/assignments` = ui-token only (A1). Осознанный гейт, но повторяющаяся работа (регулярные ревью, свипы, ретро-выгрузки) требует ручного клика каждый цикл | создатель поручения — всегда человек |
| П4 | **Существующая автоматика зашита в код.** Каждая новая периодика (свип, сканер, reaper) — релиз сервера, а не настройка; из UI её не видно, нельзя выключить/посмотреть «когда сработало» | циклы §1.3 не конфигурируемы |

**Корневая формулировка.** У борда есть очередь исполнения (assignments),
событийная шина (SSE) и даже фоновые циклы — но нет сущности «правило
автоматизации» и нет субъекта-автомата между владельцем и очередью: источник
каждого запуска — человек; вся прочая автоматика — код, а не данные.

## 3. Напряжения

**Н1. T2-гейт Security — до первого автозапуска, не после.** T2 по ADR 0009 §8
= «autostart runs without per-launch owner oversight» — любой запуск по
расписанию/событию есть T2 по построению. АРХКОМ-4 (решение 4): автодиспетчер —
T2-гейт; тот же гейт переносится сюда с усилением. Следствия: (а) per-executor
токены + реестр ARCH-9 обязательны ДО включения движка; (б) аудит старое→новое
на каждое изменение правила (паттерн `default.changed`, Amendment 2 §7);
(в) гейты цели — approved + live heartbeat, remote ineligible до R4
(Amendment 2 §5 — те же, что у дефолта); (г) kill-switch per-rule и глобальный.

**Н2. WF-1: автозапуск только валидированного.** Сегодня гейт —
archived/terminal (422); при WF-1 канонический критерий «к работе» =
`task:queue` БЕЗ `task:stage:*` (WF-1 §5.1). Правило обязано проверять
пригодность **в момент срабатывания**, не в момент сохранения правила — иначе
TOCTOU-окно, зеркальное закрытому снапшотом A2: задача могла уехать в
backlog/архив после создания расписания.

**Н3. Injection-поверхность: триггер становится полуинструкцией.** По
`ui-contract.md` §12 данные борда — не инструкции; assignment — единственная
точка инверсии именно потому, что перед ней стоят owner-action + ui-token +
снапшот (ADR 0009 §5). Автозапуск убирает owner-action из цепочки каждого
запуска. Новый вектор: писатели machine-token (reports, moves, heartbeat)
влияют на события-условия → агент дёргает событие → хук запускает другого
агента — неявный обход запрета agent→agent write (Amendment 2 §9). Митигации:
условия только по структурированным полям (state/col/project/specialist/kind),
никогда по тексту спеки или отчёта; `source_allowlist` в правиле (v1:
события ui-token-действий и серверной автоматики); контент в конверт идёт
только через существующий A2-снапшот — правило не открывает новых путей
контента к агенту.

**Н4. Freeze/L1: UI только в React.** Серверные контракты — long-lived asset
(прецеденты WF-1 §7-риск1 и ARCH-2 §3); UI автоматизации — новая секция,
значит только новый app: домен «Система», волна после Ф3 (мутации/ui-token —
Ф3, ADR 0011). Замороженный `web/` не трогаем; freeze-исключение не нужно
(урок Amendment 1: ре-хоуминг UI в React сам снял потребность в исключении).

**Н5. Durability планировщика.** Часы — wall-clock в SQLite (`next_run_at`,
паттерн `stage_since` WF-1 §6.2): рестарт-safe, даунтайм = пропуски → нужна
явная missed-политика. Дисциплина часов расширяется с двух до **трёх**
(Amendment 2 §6): presence-часы (TTL исполнителя), assignment-часы (reaper),
schedule-часы (`next_run_at`) — никогда не схлопываются: планировщик не
экспайрит поручения и не трогает presence. Single-writer SQLite → один
in-process планировщик, без распределённых локов (условие `Containerfile:30`).

**Н6. Идемпотентность повторов.** Главный guard уже структурный: ≤1 активное
поручение на задачу — срабатывание по занятой задаче даёт skipped(invariant),
а не очередь дублей. Журнал срабатываний с `UNIQUE(rule_id, run_at)` закрывает
двойной тик; CAS claim (A4) закрывает гонку поллеров.

**Н7. Rate и бюджеты.** Без них зацикленный хук (fail → on-assignment.failed
→ launch → fail) выжигает токены и аудит. Обязательны: per-rule
launches/день + cooldown; per-specialist concurrent cap; глобальный дневной
cap автозапусков; kill-switch per-rule (`enabled=0`) и глобальный (флаг
`board_meta`, по образцу kill-switch дефолта через revocation).

## 4. Варианты архитектуры

### A. Планировщик + ECA-движок in-process на борд-сервере

**Механика.** Таблицы `schedules`/`hooks` в SQLite; цикл `_scheduler_loop` в
lifespan (60 с, exception-guard — паттерн `app.py:128`); ECA-движок —
подписчик на точку эмита `_notify_and_broadcast`/переходов store. Действие
`create_assignment` идёт через существующий `store.create_assignment` с
`created_by='automation:{rule_id}'` — тот же инвариант ≤1, тот же снапшот A2,
тот же SSE `assignment.created`.

- Плюсы: ноль новой инфраструктуры; паттерн доказан пятью циклами (§1.3);
  правила/журнал/аудит в одном SQLite рядом с assignments; kill-switch
  тривиален; SSE бесплатно; серверу не нужно ничего знать о поллере.
- Минусы: аптайм борда = аптайм автоматики (пропуски при даунтайме —
  missed-политика); движок в траст-домене борда (митигируется exception-guard
  + бюджетами); cron-парсер — новая зависимость (или интервалы в v1).

### B. Cron-нога на стороне поллера (laptop)

**Механика.** Борд хранит расписание (read-only для поллера), поллер по
локальному cron сам решает «пора» и… создаёт поручение? Но `POST
/api/assignments` — ui-token only. Значит: либо ui-token на ноутбуке (ломает
A1 — машина снова может минтить поручения, reopen инъекционного вектора),
либо новый класс scheduler-token (усложнение лестницы L0–L2), либо запуск
агента вовсе без assignment (невидимое исполнение — ломает весь
observability-стек и reaper).

- Плюсы: запуск привязан к машине, где реально есть исполнитель — не плодим
  `queued` при мёртвом поллере (но это уже диагностируется: stagnation-бейдж
  возраста в очереди, ADR 0009 §4).
- Минусы: ломает A1 (или требует третьего токен-субъекта); логика в двух
  местах — расписание на борде, решение на laptop (рассинхрон, слабый аудит);
  спящий laptop = мёртвая автоматика при живом борде; несколько поллеров →
  гонки по расписанию; **T2 не снимается** — гейты те же, но проверять их
  труднее.

### C. Этапность: контракты раньше движка

**S1 — контракты без автоматики:** schema `schedules`/`hooks`/`launches`,
CRUD ui-token + аудит + SSE-резерв + бюджеты в схеме + «Запустить сейчас»
(ручной триггер — не T2). **S2 — движок** (вариант A) строго под T2-гейтом
(чеклист §6.8). **Webhooks наружу — отдельным решением после v1** (новая
egress/SSRF-поверхность и секреты адресатов; ADR 0009 §9 держит контур
«board никогда не получает inbound», outbound-адресаты расширяют модель угроз).

Ось хуков: **board-internal ECA** (действия `create_assignment` | `notify`,
замкнуто в борде) vs **outbound webhooks** (борд → внешний URL) vs оба.
Рекомендация: internal-only в v1.

### Сравнение

| Критерий | A in-process | B поллер-cron | C этапность (рекоменд.) |
| --- | --- | --- | --- |
| Новая поверхность | 2 таблицы + ~10 эндпоинтов + 1 цикл | то же + токен-субъект + логика в поллере | S1: таблицы+CRUD; S2: +1 цикл |
| T2-готовность | гейты нужны сразу | гейты те же + ломает A1 | S1 не-T2; S2 под явным гейтом |
| Durability | restart-safe, пропуски при даунтайме борда | привязана к аптайму laptop | как A (с журналом missed) |
| UI-скоуп | React после Ф3, `/system/automation` | тот же + статус на поллере | тот же; S1-UI полезен без движка |
| Риски | движок в траст-домене борда | инъекция/рассинхрон/гонки | минимальны на каждом шаге |
| Зависимость от ARCH-9 | S2-blocker | S2-blocker + токены | S1 едет до/параллельно |

## 5. Черновые контракты (S1)

    schedules: id, name, enabled,
      target_kind ('task'|'template'),            -- v1: 'task' (рецидив)
      task_id, specialist, harness, executor_id,  -- пин опционален (Am2 §5)
      trigger ('interval'|'time-of-day'), value,  -- v1 без полного cron
      window_utc (from, to; NULL = всегда),
      budget (max_runs_per_day, max_concurrent, cooldown_s),
      next_run_at, last_run_at, created_by, created_at, updated_at
    hooks:      id, name, enabled,
      on (kind из белого списка),                 -- task.moved, assignment.failed,
                                                -- assignment.expired,
                                                -- task.validation-timeout (WF-1)
      condition [{field, op, value}],             -- только структурированные поля
      source_allowlist,                           -- v1: ui-token + server
      action ('create_assignment'|'notify'), action_payload,
      cooldown_s, budget, created_by, created_at, updated_at
    launches:   id, rule_id, rule_kind, run_at,
      decision ('launched'|'skipped'|'missed'), reason,
      assignment_id, UNIQUE (rule_id, run_at)

- **Принципал.** Создание движком — internal-вызов store с
  `created_by='automation:{rule_id}'`; фильтр `GET /api/assignments?by=automation`.
  Новых HTTP-токенов не вводится; CRUD правил — ui-token, 10/60 с (домашний
  паттерн, `app.py:1806`).
- **События-источники v1 — белый список** (низкий риск циклов): `task.moved`,
  `assignment.failed`, `assignment.expired`, `task.validation-timeout`,
  `executor.offline` (notify-only). Запреты: условия по free-text; действия
  правил как триггеры других правил (anti-loop); события heartbeat.
- **Лимиты.** Глобальный cap автозапусков/день (default 20, `board_meta`);
  per-rule бюджет; глобальный kill-switch `board_meta 'automation.enabled'`.
- **Аудит.** `rule.{created,updated,toggled,deleted}` (actor, old→new),
  `scheduler.launched` (rule, assignment_id, resolved executor, spec_hash),
  `scheduler.skipped` (reason: budget | window | invariant |
  inactive-executor | not-assignable | disabled), `scheduler.missed`.
- **SSE (additive-only, §11).** Резерв `automation.rule.*`,
  `scheduler.launched` (в ленту UI-10); пер-тиковые события запрещены
  (урок per-heartbeat ban, Amendment 2 §7).
- **UI (React, после Ф3).** `/system/automation` — «Расписания | Правила» +
  журнал срабатываний; на «Обзоре» — строка «автозапуски сегодня» в блок
  «Агенты» (§2.4 концепта); состояние «движок не включён» честно видно.

## 6. Открытые вопросы (с рекомендациями PA)

1. **Рецидив vs шаблон:** один recurring-запуск на одной задаче или создание
   новой задачи из шаблона (CI-семантика)? *Реком.: v1 — рецидив на одной
   задаче: guard ≤1 уже структурный, история в одном месте; шаблоны — после
   ретро.*
2. **Действия хуков v1:** notify-only или + create_assignment? *Реком.: оба,
   но create — только от событий ui-token/серверного происхождения
   (`source_allowlist`).*
3. **Missed-runs при даунтайме:** catch-up пачкой или skip? *Реком.: skip +
   журнал missed — catch-up при бюджетах и человеческом контроле опасен.*
4. **Часовой пояс:** UTC-only? *Реком.: да — весь store в UTC (`_now()`);
   локальная зона — UI-настройка позже.*
5. **Форма триггера:** полный cron или интервал+время суток? *Реком.:
   интервалы в v1 (без парсера cron); cron — по реальному запросу.*
6. **Удалённые исполнители как цель автоматики:** ineligible до R4?
   *Реком.: да — тот же гейт, что у дефолта (Amendment 2 §5).*
7. **Место UI:** отдельный раздел vs вкладка настроек? *Реком.: отдельный
   `/system/automation` — это операционная сущность с журналом, не настройка.*
8. **Чеклист T2-гейта S2:** ARCH-9 смержен + per-executor токены в claim +
   аудит правил + бюджеты + kill-switch + ретро Ф1 (метрика ≥80%, ADR 0009
   §11)? *Реком.: да, зафиксировать как формальный гейт в ADR.*

## 7. Рекомендация PA

**Вариант C (этапность): S1 — контракты сейчас, S2 — движок варианта A под
T2-гейтом; хуки — board-internal ECA; webhooks — за пределами v1.**

1. **Строим на существующих механизмах:** очередь+CAS+снапшот+инвариант ≤1
   (идемпотентность повторов — структурная, Н6), reaper, SSE-словарь,
   `board_meta`, паттерн фоновых циклов — ничего не изобретается.
2. **A1 не ломается:** создание поручений остаётся за ui-token (владелец) или
   внутренним принципалом `automation:*` с полным аудитом; поллер по-прежнему
   только клэймит.
3. **Гейт — проверяемый чеклист, а не мнение:** S1 не создаёт T2-поверхности
   (ручной «Запустить сейчас» = обычный ui-token-запуск), S2 включается после
   закрытия чеклиста §6.8.
4. **Эволюция без переплаты:** контракты S1 инвариантны к носителю движка —
   переезд на отдельную ногу позже меняет транспорт, не семантику (тот же
   аргумент A→B, что закрыл ARCH-2 §7.4).
5. **Риск ползучести к scheduler'у заперт рамкой:** автоматизация запуска —
   отдельный домен с правилами, бюджетами, журналом и kill-switch, а не
   расширение цепочки дефолта; «кому» и «когда» никогда не смешиваются.
