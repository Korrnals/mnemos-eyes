> Связанные документы: ADR 0005 (harness identity), ADR 0006 (freeze rule), ADR 0008

## 0. Стимул владельца (исходная постановка)

1. «Взять задачу в работу» из UI должно **реально запускать агента** — с выбором
   исполнителя.
2. Работа агентов и их задач — **блэкбокс**; нужна наблюдаемость.
3. Чекпоинты/отчёты агентов должны **сами течь в карточки** — механизм отчётов есть
   (`POST /api/tasks/{id}/reports` + история), но агенты пишут вручную или не пишут.
4. Связь с **UI-10** — левый «проводник» изменений задачи и нижняя панель: им нужен
   постоянный источник событий исполнения.

## 1. Контекст и текущее состояние

### 1.1 Борд

- **Стек:** FastAPI + SQLite + SPA без сборки (ADR 0008: Python остаётся; триггер
  пересмотра записан). Развёрнут в кластере (Helm + ingress, решение SEC-3 на
  АРХКОМ-1), single worker — `uvicorn` без `--workers` (`Containerfile:30`).
- **Аутентификация мутаций:** fail-closed bearer — пустой `VESMARO_BOARD_TOKEN`
  отклоняет любую мутацию с 503, несовпадение — 401, сравнение constant-time
  (`server/app.py:1585–1604`). Токен один на всех писателей; per-клиентской
  идентичности на HTTP-слое нет.
- **SSE** (`GET /api/events`, `app.py:1605–1631`): in-process fan-out, at-most-once,
  без персистентности и resumption (Last-Event-ID не поддерживается, `ui-contract`
  §11); словарь событий **additive-only**, клиент обязан молча игнорировать
  неизвестные `kind`.
- **Модель задач:** колонки `open | in-progress | blocked | resolved | done`
  (`store.py:29`); переходы сегодня не валидируются (`move_task`, `store.py:344` —
  зеркалирование машины mnemos планируется WF-1).

### 1.2 Агентный ландшафт

- Исполнители — **GCW-специалисты** на **zcode-харнесах**, которые живут на ноутбуке
  владельца, **вне борда**; запуск агента сегодня — только вручную, владельцем,
  в своей сессии.
- **Память — mnemos**: независимый продукт со своим релизным циклом и серверной
  state machine. Инвариант WF-1: задачи трекера = mnemos-записи с тегом
  `task:queue`; очередь задач в mnemos уже обсуждается (`task-queue-mnemos-128`).
- **ADR 0005**: харнесы (среда исполнения) и специалисты (роль) — разные сущности;
  разделение должно держаться cross-system.

### 1.3 Что уже есть и на что можно опереться

| Механизм | Что даёт | Где |
| --- | --- | --- |

## 2. Проблемы (по стимулу)

| # | Проблема | Факт сегодня |
| --- | --- | --- |
| П1 | **Нет исполнения из UI.** «Взять в работу» не запускает никого: переход `open → in-progress` двигает только колонку; выбор исполнителя (`specialists[]`/`agents[]`) — данные карточки, а не триггер | действия «запустить» в API нет |
| П2 | **Нет статуса «агент реально работает».** Борд не знает, взял ли кто-то задачу, жив ли процесс агента, на каком харнесе. Сигналы только косвенные (агент сам двинул колонку, запись в mnemos) | понятия assignment в модели нет |
| П3 | **Отчёты/чекпоинты ручные.** Механизм есть (reports + SSE + история), но агент пишет отчёт только если владелец явно попросил в промпте; чекпоинты в mnemos (checkpoint-записи) в карточке не видны вообще | reports — по требованию; mnemos-чекпоинты не отображаются |
| П4 | **UI-10 без источника событий.** Проводнику изменений и нижней панели нужен поток «что агент сделал только что»; даже существующий SSE `kind:"report"` клиент молча игнорирует (неизвестный kind, `ui-contract` §11) | проводник рисовать не из чего |

**Корневая формулировка:** у борда нет понятия **assignment** (кто взял задачу, в
каком статусе исполнение, жив ли исполнитель), а у харнесов нет **inbox-механизма**
— способа узнать, что владелец назначил им работу, не спрашивая борд глазами.

## 3. Ключевой tension с ADR 0006 (freeze rule)

Freeze rule: борд = bug-fix only; **любое новое действие/сущность/секция = L1
backlog**; метрика — net feature surface борда = 0. Проблема ARCH-2 требует:
нового действия («взять в работу» → запуск), новой сущности (assignment), новых
SSE-событий, новой UI-панели. Формально — весь скоуп фича-класс, всё → L1.

Но механика исполнения не «переезжает» в L1 автоматически:

1. **L1 — другой фронтенд того же борда**, а агенты работают вне борда вообще
   (ноутбук, харнесы). Проблема — серверная интеграция + контракт, фронтенд здесь
   вторичен.
2. **Борд-сервер API — long-lived asset**, который переносится в L1 целиком
   (ADR 0006 §4: API, SSE-словарь, онтология ADR 0005). Значит контракт assignment'ов
   в любом случае строится на серверной стороне борда и потом переезжает — freeze
   защищает от дивергенции DOM-кода, а не от серверной интеграции.
3. **Прецедент WF-1**: серверная модель + автоматика объявлены long-lived asset и
   признаны допустимыми при freeze; под freeze попала только UI-фаза (через реестр
   исключений).

**Вопрос комитету (поставить явно, не решать молча).** Три рамки:

| Рамка | Суть | Последствие |
| --- | --- | --- |
| (i) Эволюция борда (freeze-исключение) | агент-механизм = развитие long-lived asset; UI — one-liner в реестре исключений | быстро, но расширяет поверхность замороженного борда — прецедент «исключение» надо держать узким |
| (ii) Фича L1 | серверный контракт проектируем сразу под L1; борд не трогаем до L1 | чисто по букве freeze, но владелец не получает запуск из UI до L1-парити (гейт ADR 0006) — стимулowner'а игнорируется |
| (iii) Отдельный компонент | агент-бридж — отдельный сервис; борд не меняется | борд не тронут, но появляется новая инфра-единица и всё равно нужен UI-контур на борде |

Позиция TL: рамку выбирает комитет; варианты §4 ниже инвариантны к выбору в том
смысле, что контракт (§5) одинаков — меняется только носитель.

## 4. Варианты архитектуры

### A. Outbox/claim — борд как очередь заданий

**Механика.** «Взять в работу» в UI пишет assignment-запись
(`queued`, исполнитель = specialist + целевой harness). Внешний **поллер** на
ноутбуке владельца (скрипт в zcode-харнесе или крон — не сервис) опрашивает
`GET /api/assignments?state=queued` с существующим bearer-токеном, делает claim
(`queued → claimed`, фиксирует identity харнеса), запускает агента локально.
Дальше — существующие API: перемещения задачи, `POST /reports`
(`intermediate` по ходу работы, `final` в конце).

- **Плюсы:** ноль новых компонентов (поллер — скрипт на машине владельца, не
  инфраструктура); всё строится на работающих механизмах (bearer, reports, SSE,
  матрица прав WF-1); контракты остаются на борд-сервере — long-lived asset по
  ADR 0006; работает «уже сегодня».
- **Минусы:** латентность = интервал опроса (кнопка → старт агента через N секунд);
  поллер — ещё один цикл, который надо не забыть запустить (нет поллера — задания
  копятся в `queued`); claim-гонки при >1 поллере (митигация: один поллер — по
  образцу single-worker борда); живость агента надо выражать самому
  (например, `intermediate`-отчёт как keep-alive + reaper по таймауту).

### B. Bridge-сервис рядом с бордом

**Механика.** Отдельный маленький сервис: очередь заданий + endpoint для харнесов
(long-poll или webhook в zcode CLI, если/когда появится), проброс статусов в борд.

- **Плюсы:** чистые контракты — assignment lifecycle живёт в одном месте; мгновенность
  (push в харнес вместо опроса); RCE-поверхность запуска изолирована от борда.
- **Минусы:** новая инфра-единица в деплое (сейчас: 1 контейнер борда + mnemos);
  безопасность запуска — новый threat model (право дёргать команду на ноутбуке
  владельца = RCE по определению, нужен свой auth и allowlist); **двойное состояние**
  (очередь в бридже + статусы в борде — новый класс рассинхронов); на текущем
  масштабе (1 владелец, единицы агентов) — оверинжиниринг. Логика ADR 0008
  применима напрямую: итерация с владельцем важнее архитектурной чистоты.

### C. mnemos-centric

**Механика.** Задания и чекпоинты — записи mnemos (тег `task:queue` уже существует);
харнесы опрашивают/слушают mnemos; борд — только UI над памятью.

- **Плюсы:** единая память — задания и знания в одном месте; graduation из WF-1
  работает как есть; чекпоинты агенты и так пишут в mnemos — источник для UI-10
  существует уже сейчас; ноль изменений борда (идеально по букве freeze).
- **Минусы:** **mnemos — не message-broker**: нет at-least-once доставки, ack/nack,
  lease на задание — «кто взял задание» без гонок не решить; опрос памяти латентнее
  и тяжелее, чем опрос очереди; семантика роутинга «кому отдать работу» — это
  очередь, а mnemos — память (делать из памяти брокер — тот же класс ошибок, что
  рассинхрон борд/mnemos, разобранный в WF-1 §5.1); mnemos недоступен → исполнение
  стоит.

### D. Гибрид A+C

**Механика.** Задания — через борд outbox/claim (вариант A: надёжная очередь
со статусами-ack). Чекпоинты — агент пишет в mnemos как знание (как уже делает) +
ключевые вехи дублирует в reports API борда (для SSE и карточки).

- **Плюсы:** каждый механизм в своём слое — команды исполнения в борде, знания
  в памяти; UI-10 получает и ленту отчётов (борд), и глубину чекпоинтов (mnemos).
- **Минусы:** два канала = два места рассинхрона; в v0 дороже чистого A.

### Сравнение

| Критерий | A outbox/claim | B bridge | C mnemos-centric | D гибрид A+C |
| --- | --- | --- | --- | --- |
| Новая инфраструктура | нет (поллер-скрипт) | **новый сервис** | нет | нет (поллер-скрипт) |
| Латентность старта | интервал опроса (секунды) | мгновенно | интервал опроса mnemos (секунды+) | как A |
| Надёжность доставки | статусы-ack в SQLite | очередь бриджа | **нет ack/lease** | как A |
| Рассинхроны | нет (одно состояние) | борд ↔ бридж | память vs реальность | борд ↔ mnemos (осознанно) |
| Безопасность запуска (RCE) | триггер на ноутбуке владельца | RCE-эндпоинт бриджа | триггер на ноутбуке | как A |
| Соответствие freeze | серверная эволюция + UI-исключение | борд не тронут, но UI всё равно нужен | ноль изменений борда | как A |
| Работоспособность сегодня | да | нет (строить) | частично (нет routing/ack) | да |

## 5. Контракты, которые придётся зафиксировать

Черновой список — независимо от выбранного варианта (меняется носитель, не семантика):

1. **Assignment lifecycle.** `queued → claimed → running → reporting → done | failed
   | cancelled`, плюс timeout-reaper для зависших. Маппинг на колонки: claim двигает
   задачу `open → in-progress` (переход разрешён, агент вправе двигать **свои**
   задачи — матрица WF-1 §4.2). Открытый подвопрос: assignment — отдельная запись
   (рекомендация: да — на задачу может быть N запусков) или состояние на самой
   задаче.
2. **Идентичность агента.** Какой харнес взял задание — по ADR 0005 (harness ≠
   specialist). Честный факт: bearer один на всех, а `agent` в reports — свободная
   строка от клиента (`store.py:738`), identity на HTTP-слое сегодня спуфится.
   Варианты: per-harness токены или identity как claim-поле с допущением
   «один владелец, доверенный контур» — уровень гарантий фиксировать явно.
3. **Поток чекпоинтов.** Kinds `intermediate | final` уже есть, supersede-семантика
   final уже есть. Расширение (heartbeat/progress) — additive по правилам
   `ui-contract` §11. Привязка mnemos-чекпоинтов к задаче — через `mnemos_tags`
   (поле в Task уже есть).
4. **SSE-события для UI.** Новые `assignment.*` kinds — additive-only. Найти и
   закрыть существующий gap: `kind:"report"` эмитится кодом (`app.py:1323–1328`),
   но в словаре `ui-contract` §11 отсутствует, и клиент его молча игнорирует —
   контракт и код надо свести в одной фазе.
5. **Security.** Запуск агента — RCE-поверхность. Зафиксировать: кто вправе
   триггерить запуск (только владелец из UI?); allowlist исполнителей (какие
   specialists вообще могут назначаться автоматически); где живёт решение «кого
   запускать» — рекомендация: на стороне поллера (машина владельца), борд только
   номинирует исполнителя; allowlist хранится у поллера, а не в борде.
6. **Лимиты.** Rate limits на новые эндпоинты по образцу существующих (reports
   30/60 с, drafts/reflect 10/60 с на клиента); лимит одновременных запусков на
   харнесе; таймаут assignment'а (reaper) — со второй фазы.

## 6. Открытые вопросы владельцу/комитету

1. **Рамка freeze (§3):** эволюция борда (исключение) vs L1 vs отдельный компонент?
   *Рекомендация TL:* серверная интеграция = эволюция long-lived asset (запись в
   реестре исключений, как WF-1); UI-фаза — one-liner в реестре или L1.
2. **Кто физически запускает агента:** поллер на ноутбуке (борд только номинирует)
   или борд дёргает харнес сам? *Рекомендация:* поллер на ноутбуке — борд в кластере
   не должен получать канал исполнения команд на машину владельца (SSH/webhook =
   новая RCE-поверхность в демилитаризованной зоне).
3. **Гарантия доставки задания:** достаточно ли at-most-once для v0 (поллер упал —
   задание висит `queued`, владелец видит и перезапускает)? *Рекомендация:* да,
   для одного владельца — достаточно; reaper/lease — вторая фаза.
4. **Идентичность на HTTP-слое:** один bearer vs per-harness токены?
   *Рекомендация:* v0 — один токен (доверенный контур, один владелец), per-harness —
   при появлении второго харнеса в контуре; зафиксировать триггер пересмотра.
5. **Первичный канал чекпоинтов:** агенты пишут reports API (борд) или борд читает
   чекпоинты из mnemos? *Рекомендация:* reports API — primary (уже интегрирован в
   SSE/карточку), mnemos-чекпоинты остаются знанием и вторичным источником для
   проводника UI-10; борд в v0 не читает чекпоинты из mnemos.
6. **Выбор исполнителя в UI:** из `specialists[]` карточки (структурированно) или
   свободным полем? *Рекомендация:* из `specialists[]` + целевой harness
   (ADR 0005) — иначе allowlist из п.5 не построить.

## 7. Рекомендация TL

**Вариант A (outbox/claim) как шаг 1, с контрактом (§5), допускающим эволюцию в B;
канал чекпоинтов — как в D: reports API primary + mnemos параллельно.**

Обоснование:

1. **Строим на существующих механизмах:** bearer-контур, reports API + SSE +
   история, матрица прав агентов WF-1, инвариант `task:queue` — ничего из этого
   изобретать не надо.
2. **Минимальная новая поверхность:** ноль новых сервисов; один внешний поллер на
   машине владельца; несколько additive-эндпоинтов на борд-сервере (long-lived asset
   по ADR 0006 — они переезжают в L1 без переделки).
3. **Безопасность:** триггер исполнения остаётся на машине владельца — борд
   номинирует, поллер решает и запускает; RCE-поверхность не растёт (вариант B
   добавляет её, вариант C не решает ack/lease).
4. **Эволюция без переплаты:** lifecycle-контракт (§5.1) одинаков для A и B —
   переход к bridge-сервису меняет транспорт, не семантику; значит выбор A сейчас
