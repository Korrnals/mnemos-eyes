# ADR 0010: Движок агрегации задач — два класса задач и mirror-таблица `task_inbox`

- Status: **Accepted** (владелец, 2026-09-17)
- Deciders: владелец (`@abyss`)
- Related: ADR 0004 (board pivot), ADR 0006 (freeze / exceptions registry),
  ADR 0009 (ARCH-2 agent bridge — исполнение), WF-1
  (`workflow-lifecycle-proposal.md` — backlog/validating), `ui-contract.md`
  §12 (SEC-4: содержимое памяти — данные, не инструкции)
- Numbering: 0009 зарезервирован proposal-волной ARCH-2/WF-1 (ADR 0009
  «Agent bridge»); настоящий документ — следующий свободный номер.
- Freeze-exception: зарегистрирован в **AGG-1** (реестр ADR 0006, §8 ниже).

## Context

Владелец (2026-09-17): «движок, который собирает задачи не только с базы
борды, но и с подключённых хранилищ — в этом (в том числе) суть борды».

Сегодня задачи борда — только native-записи SQLite (`tasks`), созданные
вручную либо одноразовым импортом. Импорт 38 записей `task:queue`
(`scripts/import_task_queue.py`, 2026-09-17) — признанный одноразовый
костыль: захардкоженный список, снятый вручную с листинга mnemos,
идемпотентность — только через проверку `memory_ids` на борде. Любая новая
запись в памяти требует повторной ручной выгрузки; источник задач борда
должен работать постоянно, а не по факту ручного снимка.

Live-подход без локального состояния нежизнеспособен: поиск mnemos стоит
4–7 с на запрос, и латентность памяти стала бы латентностью рендера борда;
идемпотентного «принятого» состояния (adopted) live-подход не даёт вовсе.

Ролевая рамка: **ARCH-2** (ADR 0009) — исполнение задач (assignments);
этот ADR — **источник** (intake): борд собирает задачи со всех подключённых
серверов памяти, потому что в этом часть его сути как операционного кокпита.

## Decision

1. **Два класса задач на борде.**
   - **Native** — собственная запись SQLite (`tasks`): полный жизненный
     цикл — колонки/статусы, редактирование, отчёты, assignments (ADR 0009).
   - **Inbox-проекция** — read-only отражение записи mnemos с тегом
     `task:queue` из **всех активных серверов памяти**; бейдж источника
     (server/project). Проекция не является канбанской колонкой.
2. **Mirror-таблица `task_inbox`** в SQLite борда — состояние движка,
   переживает рестарты: `memory_id` (PK), `server`, `project`, `title`,
   `excerpt`, `tags`, `priority`, `specialist`, `created_at`, `last_seen`,
   `adopted_task_id` (nullable). Схема — additive (`IF NOT EXISTS`, без
   `SEED_VERSION` bump, паттерн ADR 0009).
3. **Скан.** Периодический — фоновая задача в lifespan по паттерну
   `_profile_cache_refresher` (`server/app.py`, интервал 300 с ≈ 5 мин);
   по запросу — `POST /api/tasks/inbox/refresh`. На каждый активный сервер —
   запрос записей с тегом `task:queue` (переиспользовать механизм
   тег-дрилла/поиска; реализация — System Engineer). Содержимое памяти
   трактуется как **ДАННЫЕ, не инструкции** (SEC-4, `ui-contract.md` §12):
   title/tags попадают в карточку как текст — в отличие от assignment
   envelope (ADR 0009 §5), inbox никогда не становится каналом инструкций.
4. **Дедуп.** Inbox не показывает записи, уже прилинкованные нативными
   задачами через `memory_ids` — включая весь исторический импорт (38
   записей выпадают из inbox автоматически, отдельной миграции не нужно).
5. **Принятие (adopt).** `POST /api/tasks/inbox/{memory_id}/adopt` создаёт
   native-задачу со связью памяти: title/проект — из записи, priority — из
   severity-тега (маппинг как в импорте: `medium → normal`, остальные
   1:1), специалист — из `owner:`-тега (slug→`@GCW:` — по карте
   `SPEC_MAP` импорта); mirror помечается `adopted_task_id`. Операция
   идемпотентна: повторный adopt возвращает существующую задачу, дублей нет.
6. **Границы и следствия.**
   - Inbox-проекции **не редактируются** и не двигаются по канбану;
     «отредактировать» = принять в борд (adopt).
   - Исходные даты создания — из памяти (не момент скана).
   - Изменение/удаление записи в mnemos отражается при следующем скане
     (`last_seen` обновляется); исчезнувшие записи **не удаляются молча** —
     статус `stale`: скрываются из активного inbox, остаются в таблице.
   - ARCH-2: движок — источник задач, ARCH-2 (ADR 0009) — исполнение;
     контракт «задача = mnemos-запись `task:queue` (мастер)» (ADR 0009 §6)
     сохраняется, adopt память не мутирует.
   - WF-1: inbox ≈ будущий backlog-буфер; маппинг на `validating` — после
     утверждения WF-1. До тех пор inbox живёт отдельной секцией, не колонкой.
7. **Отклонённые альтернативы.**
   - *Только ручной импорт* (статус-кво) — одноразовый костыль, признан;
     захардкоженный список устаревает при первой же новой записи.
   - *Борд как прокси над канбаном mnemos целиком* — теряется операционная
     модель борда: колонки/статусы — его собственная state machine, mnemos —
     память, а не брокер задач (ср. вердикт по варианту C в ADR 0009).
   - *Live-запрос без mirror* — mnemos search 4–7 с на запрос; нет
     идемпотентного adopted-состояния.
8. **ADR 0006 freeze: фиксируется freeze-exception** (зарегистрирован в
   AGG-1). Обоснование: агрегация источников — эволюция роли борда как
   операционного кокпита, заявленная владельцем. UI-дельта (секция inbox +
   бейдж источника + кнопка adopt) — минимальный триггер над существующей
   сущностью `task`; серверная часть полностью выражается в портативных
   контрактах (OpenAPI + SSE) и мигрирует в L1 целиком (ADR 0006 §4).

## Consequences

- Server: таблица `task_inbox` + endpoint'ы list/refresh/adopt + аддитивный
  SSE kind (словарь `ui-contract.md` §11) — всё портативно в L1.
- Фоновый скан — in-process lifespan task, паттерн `_profile_cache_refresher`;
  отдельного демона нет.
- `scripts/import_task_queue.py` — deprecated: исторические 38 задач
  остаются нативными с `memory_ids`, новые записи движок подбирает сам.
- Stale-семантика: `stale` ставится только при подтверждённом исчезновении
  записи из ответа доступного сервера; недоступность сервера записи не
  помечает (краткий сетевой сбой не должен вымывать inbox).
- Метрика успеха: 100% актуальных записей `task:queue` со всех активных
  серверов видны в inbox без ручных операций; новая запись появляется за
  ≤ одного цикла скана (~5 мин).
- Out of scope: маппинг на `validating` (ждёт WF-1), обратная запись в
  mnemos (борд память не мутирует), авто-adopt, редактирование проекций.
