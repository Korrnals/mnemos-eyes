# ADR 0016: Cortex Workspace — фаза 1: read-only агрегация сессий + relay-продолжение (вариант C)

- Status: **Proposed — awaiting owner ratification** (АРХКОМ 2026-09-23:
  вердикт комитета = рекомендация, не старт. Директива владельца
  2026-09-22: дизайн → архком → реализация; фаза 1 стартует только после
  ратификации владельца — прецедент ADR 0014)
- Deciders: АРХКОМ 2026-09-23 — Product Architect (автор дизайн-бумаги),
  Analytics Lead, Senior Security Engineer, Senior System Engineer
  (приглашён председателем); председатель и инженерный владелец решения —
  `@GCW: Tech Lead`; владелец реализации — `@GCW: Senior System Engineer`
  (ядро 1–5), UI — `@GCW: Senior Frontend Developer`; ратификация — владелец
- Related: ADR 0009 (токен-сплит ui/machine — ратифицирован, задаёт
  классы доступа), ADR 0012 (device-токены `mnd_`; `claim_token` §3),
  ADR 0014 (owner-session cookie — чат-SSE наследует его модель),
  mesh ADR-0018 (agent-gateway boundary — W4-периметр),
  mesh ADR-0021 (data topology write orchestration), ROADMAP-v2 §2.3

## Context

Директива владельца (2026-09-22, дословно по интенту): секция Cortex для
задач и сессий — видеть ВСЕ сессии всех подключённых нод/хостов
(zcode/vscode/pi) без прыжков по консолям; выбирать подключённого агента,
говорить и рулить; работать откуда угодно (телефон → Кортекс → сессия).

Главный инвариант — **NO-DRIFT**: работа, сделанная через Кортекс, видна
при позднейшем локальном открытии (vscode/zcode) и наоборот; Кортекс
дополняет «старый способ» работы, никогда не заменяет его. Формула
Tech Lead: один источник истины на сессию = стор харнесса на его хосте;
**Кортекс = view + relay, никогда форк** (ROADMAP-v2 §2.3 — cockpit over
autopilot, компоненты остаются самодостаточными).

Дизайн-бумага (ветка `docs/cortex-workspace-design`) предложила вариант C:
read-only агрегация сессий всех харнессов (нога B) + реле-продолжение
собственных zcode-сессий через headless-харнесс на хосте-владельце стора
(нога A). Комитет 2026-09-23 принял дизайн как основу фазы 1 с
обязательными правками чартера (8 amendments, ратифицированный текст —
§7 дизайн-бумаги @ a52d4d3) и зафиксировал: NO-DRIFT выполняется
конструкцией, а не дисциплиной, — стор пишет только сам харнесс.

Вердикт комитета = рекомендация. Фаза 1 стартует только после ратификации
владельца; первый компонент — реестр identity-triple.

## Decision

Принять вариант C дизайн-бумаги как основу фазы 1: **B-агрегация +
zcode-relay**. Транскрипты — доказательный материал: read-only везде,
где Кортекс их читает; писать в стор может только сам харнесс.

### 1. Нога B — видимость: read-only агрегация

- Хостовые сканеры в семействе поллера тикают сторы (push листинга на
  борд, presence-piggyback); присутствие ≠ живость сессии (двухчасовая
  дисциплина сохраняется).
- Ридеры строго read-only: zcode `db.sqlite` в `mode=ro` — без
  rollout/model-io; vscode — JSONL + капы, конверт-v3 c kind:1-патчами;
  pi — parentId. Анти-write-тесты на каждое семейство ридеров.
- Реестр identity-triple `(harness, host, native-id)` — первый компонент
  фазы: одна активная регистрация на имя, конфликт = громкий отказ;
  host-binding 1:1; host-имя self-asserted → рендер «unverified»;
  nullable `acp_session_id`.

### 2. Нога A — relay-продолжение: отдельный режим поллера

- Реле — **отдельный режим семейства поллера** (свой флаг/unit-файл,
  та же токен-лестница), никогда код внутри claim-цикла:
  recovery-семантика сессий ≠ assignment-sweep.
- Capability `session-relay` default OFF; bind loopback; удалённая
  досягаемость — только через W4 mTLS; executor-токен, никаких
  board-классовых кредов за пределами хоста.
- Спавн headless-харнесса (прецедент `zcode-headless.sh`) +
  `--resume sess_<id>`; per-session мьютекс писателя (GUI+headless
  конкурентная запись в zcode-стор — WAL, busy_timeout).
- Промпт — stdin/JSON или app-server (факт-проверка до старта
  компонента 4), **никогда argv**; логи hash+длина; spool 0600 + purge.
- Recovery: процессы помечаются мёртвыми, сессии в реестре живут;
  drain-ритуал перед обновлениями рантайма.
- Триггер выделения моста в отдельный unit: реле-нагрузка морит
  claim-цикл → перенастройка, не рефакторинг.

### 3. Чат-транспорт: ingest-binding + in-memory ring-buffer + authenticated SSE

- Поллер → борд: POST-чанки `(session_id, seq)` по executor-токену с
  **ingest-binding** — чанк принимается только в сессию,
  зарегистрированную за этим executor'ом; чужой triple → 403 + аудит.
- seq-монотонность gap=hold; капы размера и рейта.
- Борд держит in-memory bounded ring-buffer (без диска, wipe при
  eviction) — единственный источник GET-хвоста; транскрипты no-persist.
- Браузер → authenticated per-session SSE: cookie ADR 0014;
  re-валидация на flush через revocation-флаг + периодический полный
  ре-хеш; lifetime ≤21600; logout рвёт стримы; reconnect = GET-хвост
  по seq.
- Словарные `session.*` события — additive-only в `/api/events`,
  только метаданные (превью кламп + маскирование); чат-стрим в общий
  `/api/events` не идёт.
- Cross-check монитор: хвост чанков против хвоста стора.

### 4. Идентичность и доступ: телефон = ui-класс; mnd_ = metadata-only

- Два класса доступа: **ui** (owner-cookie: транскрипты, Tier-B руление
  своих сессий, чат-SSE) и **mnd_** (metadata-only; транскрипты
  запрещены — записанное решение комитета).
- Телефон владельца = обычный браузер с owner-session cookie через
  VPN = ui-класс. Условия Security: единый TLS-ingress путь lab-CA
  (без plain-http через VPN-overlay); one-command ритуал потери
  устройства (ротация ui-токена + DELETE) в RUNBOOK; документированная
  гигиена браузера (без account-sync).
- Триггер step-up (WebAuthn): любое расширение экспонирования за
  пределы устройств владельца.
- A-leg continuation только для сессий relay-происхождения или явно
  усыновлённых typed-confirm; send-путь не резолвит чужой triple — 404.

### 5. ACP — contract shape only

ACP v1 ратифицирован как **форма контракта** (шейпы + nullable
`acp_session_id`), не транспорт и не слой фазы 1. Адаптерный слой — по
триггеру первого реального ACP-native онбординга; ACP не считается
принятым до первого онбординга.

### 6. Hermes → T004; inject → v2-гейт

- Hermes-нога вынесена до T004: pod-exec-ридер = выбрасываемый код
  (T004 заменит путь), директива владельца ногу не требует; hermes =
  known-gap в метрике видимости (per-harness).
- Inject в чужие живые сессии — v2 за отдельным гейтом «до inject»:
  threat-model до кода; второй human-гейт на канале вне контроля
  отправителя; confirm по hash+длине промпта; `claim_token`
  (ADR 0012 §3).

### 7. Charter amendments — ратифицированный текст

Восемь правок чартера — обязательные части фазы-1 (ратифицированный
текст: дизайн-бумага §7 @ a52d4d3):

1. **Телефонная нога** — телефон = ui-класс через VPN; `mnd_`
   metadata-only; транскрипты ui-класс, no-persist на борде; три
   условия Security + триггер step-up.
2. **Реле = отдельный режим поллера** — свой флаг/unit-файл, та же
   токен-лестница, никогда внутри claim-цикла; relay-сессии переживают
   рестарты executor'а (assignment-sweep их не фейлит); per-session
   writer mutex; drain-ритуал.
3. **Чат-транспорт** — POST-чанки с ingest-binding, gap=hold, капы;
   in-memory ring без диска как единственный GET-хвост;
   authenticated per-session SSE по cookie ADR 0014; `session.*` в
   `/api/events` metadata-only; cross-check монитор.
4. **Расщепление security-гейтов** по грани «раньше поверхности» — до
   первого relay-дыма / до UI-показа владельцу (полный список —
   Security gates ниже); inject v2 = отдельный pre-code threat-model.
5. **Hermes отложен до T004** — метрика видимости per-harness; hermes =
   known-gap до T004.
6. **Нейминг** — UI говорит «сессия харнесса» с первого дня; «Cortex» =
   внутренний коднейм до владелеческой проверки внешней коллизии
   «Cortex Code».
7. **Acceptance gates ретро-окна** — 5 гейтов приёмки (ниже); окно
   стартует после приёмки ядра 1–5, до ≥5 продолжений или 4 недели.
8. **Pre-phase чеклист** — ручной замер SSH-базовой линии; пилотный
   hysteria-звонок с телефона; решение владельца по 6-часовому
   cookie-lifetime; часовая факт-проверка app-server vs stdin до
   компонента 4.

## Alternatives rejected

- **Отдельный bridge-сервис вместо расширения семейства поллера** —
  перестраивает супервизию/обновления/токены ради имени процесса;
  прецедент ADR 0009 B остаётся верным.
- **Свой протокол моста** — воссоздал бы N×M-клей, который ACP убрал;
  дифференциаторы Кортекса живут выше протокола.
- **ACP-адаптеры в фазе 1** — ни одна v1-нога ACP не требует; слой
  ради слоя.
- **Транскрипты для mnd_-класса** — размывает классовую семантику
  ADR 0009/0012; флагманский кейс (телефон владельца) закрывается
  ui-классом.
- **Inject в чужие live-сессии в v1** — самый рискованный класс
  действия; директивой не требуется.
- **Промпт через argv** (паттерн zcode-headless.sh) — утечка в
  `/proc/*/cmdline`; только stdin/JSON или app-server.
- **Чат-стрим в общем `/api/events`** — неаутентифицированный fan-out
  доказательного материала.
- **Hermes pod-exec-ридер в v1** — выбрасываемый код (T004 заменит
  путь) + новый surface в ревью.
- **Перевыпуск глобальных session-id** — тройка
  `(harness, host, native-id)` несущая; рендер self-asserted имён
  «unverified» вместо синхронизации имён.

## Security gates (расщепление дым/релиз)

Грани расщепления — «до поверхности»: блокеры встают раньше той
поверхности, которую защищают.

**До первого relay-дыма:**

- №2 — provenance-only continuation (только relay-происхождение или
  typed-confirm усыновление);
- №3 — промпт stdin/JSON, логи hash+длина, spool 0600 + purge;
- №7 — bind loopback + досягаемость только W4 + capability
  `session-relay` default OFF;
- №4 (ingest-часть) — ingest-binding чанков;
- №9 (read-only-часть) — открытие сторов в read-only;
- №8 (in-memory-часть) — дисциплина in-memory ring-buffer.

**До UI-показа владельцу:**

- №1 — 404 на чужой triple в send-пути (серверно, не скрытие в UI);
- №4 полностью — SSE-доставка: re-валидация, payload metadata-only;
- №5 — записанное решение «mnd_ не получает транскрипты в v1»;
- №6 — host-binding 1:1 с громким отказом на конфликт;
  «unverified»-рендер self-asserted имён;
- №8/№9 полностью — капы, zcode-ридер без rollout/model-io,
  анти-write-тесты по семействам ридеров;
- №10 редуцированно — ACP-шейпы внутренние, сетевого ACP нет;
  SDK-пинн и ревью адаптеров = гейт первого реального адаптера.

**Inject (v2, за отдельным гейтом «до inject»):** threat-model до кода;
два human-гейта; подтверждение на канале вне контроля отправителя;
confirm по hash+длине; `claim_token` (ADR 0012 §3).

## Acceptance gates (ретро-окно фазы 1)

Окно стартует после приёмки ядра 1–5; длится до ≥5 продолжений
или 4 недели.

1. **Видимость:** список ≥95% per-harness (zcode/vscode/pi)
   аудит-скриптом; полный транскрипт ≥90% — диагностика → гейт при
   провале; hermes = known-gap до T004.
2. **Продолжения:** ≥5 успешных relay-продолжений zcode-сессий
   (рабочие, не тестовые), ≥2 с телефона через VPN ≤5 мин;
   аудит-события несут device-class / network-path / session-host
   (метрика фальсифицируема).
3. **Дрифт:** ноль инцидентов С ДЕТЕКТОРОМ — определение инцидента
   закоммичено до окна; сверка session-id + число сообщений +
   локальное открытие после каждого продолжения; счётчик ведётся с
   первого relay-развёртывания (инвариант, не оконная метрика).
4. **Time-to-continue:** p50≤60с / p95≤120с LAN; ≤5 мин VPN;
   SSH-базовая линия замерена до старта фазы.
5. **Границы:** ноль fake-input на read-only; offline-хост виден ≤30с;
   счётчик vscode-тупиков с первого дня; свежесть ≤60с p95 end-to-end
   по логам чанков.

## Consequences

**Фазирование (контракт §4):**

| Фаза | Содержание | Сложность | Гейт |
| --- | --- | --- | --- |
| P0 pre-flight | SSH-базовая линия (ручной замер); пилотный hysteria-звонок с телефона; факт-проверка app-server vs stdin; решение владельца: ратификация + 6ч cookie | S | владелец + часовые проверки |
| P1 — компонент 1 | Реестр identity-triple + API листинга + link memory_id + два часа (presence/store-activity) + host-binding 1:1 + origin-колонка | M | ратификация владельца |
| P2 — компоненты 2–3 | `session.*` kinds (S); zcode-сканер mode=ro + activity-clock (M, анти-write-тесты) | M | после 1 |
| P3 — компоненты 4–5 | Реле-режим (L: мьютекс, recovery, drain, stdin/app-server, spool-гигиена); auth SSE + ring-buffer + ingest-binding (M) | L+M | после 1; блокеры «дыма» до первого прогона |
| P4 — компоненты 6–7, 9 | pi-ридер (S); vscode-ридер (M, kind:1-патчи + капы); ACP-шейпы (S: ADR-заметка + nullable колонка) | M | по мере рук |
| P5 — компонент 10 | Workspace UI (лист, пикер, чат-панель, read-only, task-binding; «сессия харнесса» с первого дня) | L | после 1–5; блокеры «релиза» до UI-показа |
| Retro-окно | после приёмки ядра 1–5; до ≥5 продолжений или 4 недели | — | acceptance-гейты |

Бэкенд-ядро 1–5 ≈ **3–4 недели одного инженера**; retro-окно — после
ядра. Hermes-ридер в фазу 1 не входит (known-gap до T004).

**Принятые остаточные риски (контракт §5):**

| Риск | Митигация | Почему принято |
| --- | --- | --- |
| Host integrity relay-хоста (малварь в UID стора = всё) | loopback + W4 mTLS + capability flag + аудит | тот же уровень доверия, что локальная работа сегодня |
| Компрометация борда = кросс-хостовое раскрытие транскриптов | no-persist, ui-класс, аудит, вычищаемые буферы | single-tenant LAN+VPN; пересмотр при любом расширении экспонирования |
| Украденный разблокированный телефон = транскрипты + typed-confirm | только own-сессии, нет inject, one-command ритуал потери, гигиена браузера | предел ущерба = own-сессии; step-up WebAuthn по триггеру расширения |
| Cookie-replay ≤ idle-6ч | стримы ≤ того же TTL | принят ADR 0014 |
| GUI+headless конкурентная запись в zcode-стор (WAL, busy_timeout) | per-session мьютекс реле | вендор-поддерживаемая схема; monitor |
| Parse-зависимость от внутренних форматов (22 миграции zcode, конверт v3 vscode, parentId pi) | read-only ридеры, капы, трекинг миграций | потеря видимости при апгрейде ≠ порча стора |
| Рестарт relay-хоста убивает ходы mid-turn | drain-ритуал, честный UI-статус, WAL стора | дрифта нет; стор цел |
| Подделка чанков скомпрометированным executor-токеном | ingest-binding + cross-check монитор (хвост чанков vs хвост стора) | детекция, не превенция — принять с монитором |

**Открытые вопросы:**

1. Владелец: ратификация этого ADR — фаза 1 стартует только после.
2. Владелец: 6-часовой cookie-lifetime = ре-логин с телефона несколько
   раз в день — осознанное решение?
3. Владелец: внешняя проверка коллизии «Cortex Code» до любого внешнего
   употребления имени.
4. До компонента 4: app-server vs stdin-промпт (часовая факт-проверка,
   read-only прогон).
5. W4 loopback-ingress расписание — от него зависит B-нога удалённых
   хостов (при сдвиге — деградация до ноут-сторов + known-gap).
