## Context

Директива владельца (2026-09-22, дословно по интенту): секция Cortex для
задач и сессий — видеть ВСЕ сессии всех подключённых нод/хостов
(zcode/vscode/pi) без прыжков по консолям; выбирать подключённого агента,
говорить и рулить; работать откуда угодно (телефон → Кора → сессия).

Главный инвариант — **NO-DRIFT**: работа, сделанная через Кору, видна
при позднейшем локальном открытии (vscode/zcode) и наоборот; Кора
дополняет «старый способ» работы, никогда не заменяет его. Формула
Tech Lead: один источник истины на сессию = стор харнесса на его хосте;
**Кора = view + relay, никогда форк** (ROADMAP-v2 §2.3 — cockpit over
autopilot, компоненты остаются самодостаточными).

Дизайн-бумага (ветка `docs/cortex-workspace-design`) предложила вариант C:
read-only агрегация сессий всех харнессов (нога B) + реле-продолжение
собственных zcode-сессий через headless-харнесс на хосте-владельце стора
(нога A). Комитет 2026-09-23 принял дизайн как основу фазы 1 с
обязательными правками чартера (8 amendments, ратифицированный текст —
§7 дизайн-бумаги @ a52d4d3) и зафиксировал: NO-DRIFT выполняется
конструкцией, а не дисциплиной, — стор пишет только сам харнесс.

Раунд улучшений АРХКОМ (2026-09-24, синтез председателя — mnemos
`136c2a84`) пересобрал rev.1 по трём осям: **sequencing** —
горизонтальные фазы P1–P5 заменены вертикальными срезами, каждый
доставляет пользу сам по себе; **поверхность** — чат v1 упрощён до
перечитывания хвоста стора, реле выделен в отдельный unit-процесс
(реверс по числам), security перебалансирован (step-up PIN,
confirm-режим, redaction choke-point, блокеры 10→8); **приёмка** —
North Star «дни самостоятельного входа владельца» + guardrails, прежние
гейты стали диагностикой. Изменения внесены как ратифицированный синтез,
без смягчений.

Вердикт комитета = рекомендация. Фаза 1 стартует только после
ратификации владельца; первый шаг — контракт-first неделя 0 (OpenAPI-шейпы
срезов 1–3 + UI-моки).

## Decision

Принять вариант C дизайн-бумаги как основу фазы 1: **B-агрегация +
zcode-relay**. Транскрипты — доказательный материал: read-only везде,
где Кора их читает; писать в стор может только сам харнесс. Rev.2
пересобирает sequencing и поверхность, не меняя инварианта.

### 1. Нога B — видимость: read-only агрегация

- Хостовые сканеры в семействе поллера тикают сторы (push листинга на
  борд, presence-piggyback); присутствие ≠ живость сессии (двухчасовая
  дисциплина сохраняется).
- Ридеры строго read-only: zcode `db.sqlite` в `mode=ro` — без
  rollout/model-io; на холодном старте — **WAL-snapshot-fallback**
  (чтение через снимок, никогда открытие на запись); vscode — JSONL +
  капы, конверт-v3 c kind:1-патчами (полный транскрипт vscode —
  known-gap среза 2; списки и превью — есть); pi — parentId.
  Анти-write-тесты на каждое семейство ридеров.
- Реестр — **derived-таблица `(executor_id, native_id)`** поверх
  существующих `executors` (rev.2 заменила церемонию регистрации
  identity-triple): host по построению не self-asserted — исполнитель
  уже enrolled с привязкой хоста; инвариант — `UNIQUE executors.host`
  + аудит (~20 строк). Громкое разрешение конфликтов хоста — в
  send-путь среза 3, не блокер видимости. `link memory_id` — срез 2.
  ACP-колонка/заметка выброшены из фазы 1: восстановление = одна
  миграция по триггеру первого реального адаптера.
- **Единый redaction choke-point**: один модуль (pattern-pack
  маскирования), одна точка на пути выдачи транскриптов и превью — всё,
  что уходит в UI, проходит только через него.

### 2. Нога A — relay-продолжение: отдельный unit-процесс

- Реле — **отдельный unit-процесс `vesmaro-session-relay.service` того
  же семейства**, что и assignment-поллер (та же токен-лестница, тот же
  паттерн супервизии). Rev.2 реверсирует позицию rev.1 «режим поллера»
  по числам: релейная нагрузка конкурирует с claim-циклом за один
  процесс; отдельный unit снимает конкуренцию по построению. Никогда —
  код внутри claim-цикла: recovery-семантика сессий ≠ assignment-sweep.
  Relay-сессии переживают рестарты executor'а (assignment-sweep их не
  фейлит); drain-ритуал перед обновлениями рантайма.
- Capability `session-relay` default OFF; bind loopback; удалённая
  досягаемость — только через W4 mTLS; executor-токен, никаких
  board-классовых кредов за пределами хоста.
- **Дефолт реле = confirm-режим**; `yolo` = явный per-session opt-in с
  аудитом, никогда дефолт.
- **Step-up PIN на включение руления**: TTL ~15 мин, по умолчанию
  выключен; чтение — без step-up. WebAuthn остаётся потолком при любом
  расширении экспонирования за пределы устройств владельца.
- Промпт — stdin/JSON или app-server; **app-server — приоритет для
  WRITE-ноги** (факт-чек P0 на неделе 0; чтение всегда только
  `mode=ro`); никогда argv; логи hash+длина.
- **Очередь промптов — in-memory внутри релея** (rev.2: дисковый спул
  0600 отвергнут — ложное чувство доставки + лишняя поверхность
  секретов) + честный статус «не доставлено — повторите» в UI.
- Спавн headless-харнесса (прецедент `zcode-headless.sh`) +
  `--resume sess_<id>`; per-session мьютекс писателя (GUI+headless
  конкурентная запись в zcode-стор — WAL, busy_timeout).
- **E2E-шифрование чата недостижимо без форка харнесса** (нарушение
  NO-DRIFT); потолок v1 = lab-CA TLS на ingress. Зафиксировано как
  граница, не как долг.
- Recovery: процессы помечаются мёртвыми, сессии в реестре живут.

### 3. Чат v1 — перечитывание хвоста стора

- **Промпт**: POST-команда в реле (ui-класс; confirm-режим; аудит).
- **Сигнал**: словарное `session.updated` (только метаданные) — поллер
  сообщает борду, что стор сессии изменился.
- **Чтение**: браузер тянет хвост сессии **authenticated GET по
  seq-курсору через B-ногу** — тот же transcript-serving путь, что и
  read-only просмотр; на борде нет второго буфера контента, стор —
  единственный источник истины.
- Свежесть ≤60с p95 end-to-end (диагностический гейт).
- **Прежний чат-транспорт rev.1** (POST-чанки с ingest-binding +
  in-memory ring-buffer + authenticated SSE) — приложение «v2
  настоящий стриминг»; триггер — «владельцу не хватает плавности». До
  триггера не строится.
- Словарные `session.*` события — additive-only в `/api/events`, только
  метаданные (превью кламп + маскирование через redaction choke-point).

### 4. Идентичность и доступ: телефон = ui-класс; mnd_ = metadata-only

- Два класса доступа: **ui** (owner-cookie: транскрипты, руление своих
  сессий с step-up PIN, GET-хвост чата) и **mnd_** (metadata-only;
  транскрипты запрещены — записанное решение комитета).
- Телефон владельца = обычный браузер с owner-session cookie через
  VPN = ui-класс. Условия Security: единый TLS-ingress путь lab-CA
  (без plain-http через VPN-overlay); one-command ритуал потери
  устройства (ротация ui-токена + DELETE) в RUNBOOK + **кнопка
  «заблокировать устройство» в UI**; документированная гигиена
  браузера (без account-sync).
- **Аудит `session.transcript_viewed`**: каждое чтение транскрипта
  (полного или live-tail) несёт device-class / network-path /
  session-host.
- A-leg continuation только для сессий relay-происхождения или явно
  усыновлённых typed-confirm; send-путь не резолвит чужой triple —
  404. **Первый релейный сценарий — НОВАЯ сессия с телефона**
  (relay-origin по построению, provenance-гейты её не касаются);
  продолжение существующей — второй сценарий.
- `mnd_`-стена с объяснением (почему транскрипты запрещены и что
  делать), не голый 403.

### 5. ACP — contract shape only; гейт = CI-трипвайр

ACP остаётся формой контракта, не транспортом и не слоем фазы 1.
ACP-колонка/заметка выброшены из фазы 1 (восстановление = одна миграция
по триггеру первого адаптера). Релиз-гейт сведён до **CI-трипвайра**:
строка «сетевого ACP нет» + автоматическая проверка отсутствия ACP-SDK
в зависимостях. Адаптерный слой — по триггеру первого реального
ACP-native онбординга; ACP не считается принятым до первого онбординга.

### 6. Hermes → T004; inject → v2-гейт

- Hermes-нога вынесена до T004: pod-exec-ридер = выбрасываемый код
  (T004 заменит путь), директива владельца ногу не требует; hermes =
  known-gap в метрике видимости (per-harness).
- Inject в чужие живые сессии — v2 за отдельным гейтом «до inject»:
  threat-model до кода; второй human-гейт на канале вне контроля
  отправителя; confirm по hash+длине промпта; `claim_token`
  (ADR 0012 §3).

## Alternatives rejected

- **Реле как режим поллера** (позиция rev.1) — снята в rev.2 по числам:
  релейная нагрузка конкурирует с claim-циклом за один процесс;
  отдельный unit-процесс `vesmaro-session-relay.service` того же
  семейства. Реверс зафиксирован честно; прецедент ADR 0009 B не
  затронут (семейство процессов и токен-лестница сохраняются).
- **Свой протокол моста** — воссоздал бы N×M-клей, который ACP убрал;
  дифференциаторы Коры живут выше протокола.
- **ACP-адаптеры в фазе 1** — ни одна v1-нога ACP не требует; слой
  ради слоя. Остаточный риск прикрыт CI-трипвайром.
- **Транскрипты для mnd_-класса** — размывает классовую семантику
  ADR 0009/0012; флагманский кейс (телефон владельца) закрывается
  ui-классом.
- **Inject в чужие live-сессии в v1** — самый рискованный класс
  действия; директивой не требуется.
- **Промпт через argv** (паттерн zcode-headless.sh) — утечка в
  `/proc/*/cmdline`; только stdin/JSON или app-server.
- **Дисковый спул промптов 0600** — отвергнут в rev.2: ложное чувство
  доставки + секрет-поверхность; in-memory очередь релея + честный
  статус «не доставлено — повторите».
- **E2E-шифрование чат-канала** — невозможно без форка харнесса
  (нарушение NO-DRIFT); потолок v1 = lab-CA TLS.
- **Церемония регистрации identity-triple** — заменена derived-таблицей:
  host by construction (enrollment исполнителя), `UNIQUE executors.host`
  + аудит; рендер «unverified» больше не нужен.
- **Чат-стрим в общем `/api/events`** — неаутентифицированный fan-out
  доказательного материала.
- **Hermes pod-exec-ридер в v1** — выбрасываемый код (T004 заменит
  путь) + новый surface в ревью.
- **Перевыпуск глобальных session-id** — пара (executor, native-id)
  несущая; отдельной синхронизации имён нет — хост уже привязан
  enrollment'ом.

## Security gates (rev.2: консолидация 10→8)

Грани — «до поверхности»: блокеры встают раньше той поверхности,
которую защищают. В rev.2 UI-поверхность появляется уже в срезе 1,
поэтому грань «до UI-показа» стартует раньше, чем в rev.1.

**Блокеры (8):**

1. **Двусторонний triple-binding** (экс-№1 + №4-ingest): send-путь —
   чужой triple → 404 (серверно, не скрытие в UI); ingest-грань —
   `session.updated` принимается только от executor'а, владеющего
   сессией. Две точки энфорсмента, распределяются по граням дым/релиз.
2. **Provenance-only continuation**: только relay-происхождение или
   typed-confirm усыновление; новая сессия с телефона = relay-origin
   по построению.
3. **Промпт-гигиена**: stdin/JSON или app-server, никогда argv; логи
   hash+длина; in-memory очередь релея + честный статус «не доставлено
   — повторите» (спул 0600 отвергнут).
4. **Transcript-serving gate** (экс-№8): authenticated GET по
   seq-курсору + redaction choke-point + re-валидация сессии на каждом
   ответе; превью — тот же путь с среза 1.
5. **mnd_ = metadata-only**: транскрипты запрещены (записанное решение);
   стена с объяснением.
6. **Host-binding**: `UNIQUE executors.host` + аудит; громкое разрешение
   конфликтов — в send-путь среза 3.
7. **Реле-периметр**: bind loopback + досягаемость только W4 mTLS +
   capability `session-relay` default OFF + confirm-режим по умолчанию
   (yolo = per-session opt-in с аудитом) + step-up PIN на включение
   руления.
8. **Read-only инвариант ридеров**: `mode=ro` + WAL-snapshot-fallback на
   холодном старте; zcode-ридер без rollout/model-io; vscode/pi — без
   записи; анти-write-тесты по семействам.

**ACP — CI-трипвайр** (не ручной релиз-блокер): строка «сетевого ACP
нет» + автоматическая проверка отсутствия ACP-SDK в зависимостях.

**Распределение по граням:**

- **До UI-показа владельцу (срез 1):** №4 (превью), №5, №6, №8.
- **До первого relay-дыма (срез 3):** №1, №2, №3, №7; №4 в полном виде
  (GET-хвост чата + live-tail шага 1.5).

**Inject (v2, за отдельным гейтом «до inject»):** threat-model до кода;
два human-гейта; подтверждение на канале вне контроля отправителя;
confirm по hash+длине; `claim_token` (ADR 0012 §3).

## Acceptance (rev.2: North Star + guardrails; ретро-окно после среза 3)

**North Star — «дни самостоятельного входа владельца»:**

- ≥5 дней из 4 недель: владелец зашёл в Кору сам;
- рост неделя к неделе;
- ≥2 дня с продолжением (relay-действие);
- фальсифицируемость — prompt-log: каждый вход и промпт оставляют
  проверяемый след.

**Guardrails (2):**

1. **Ноль дрифта С ДЕТЕКТОРОМ** — определение инцидента закоммичено до
   окна; сверка session-id + число сообщений + локальное открытие после
   каждого продолжения; счётчик с первого relay-развёртывания
   (инвариант, не оконная метрика).
2. **Старый способ не сломался** — 0 регрессий локальной работы +
   целостность стора.

**Прежние 5 гейтов = диагностика / релиз-блокеры** (не мера успеха):
видимость ≥95% (список) / ≥90% (транскрипт) per-harness с аудит-скриптом;
продолжения ≥5 рабочих, ≥2 с телефона ≤5 мин, с device-class /
network-path / session-host в аудите; time-to-continue p50≤60с / p95≤120с
LAN, ≤5 мин VPN, SSH-базовая линия замерена до старта; границы (ноль
fake-input на read-only, offline-хост виден ≤30с, vscode-тупики с
первого дня); свежесть ≤60с p95 end-to-end.

**Pre-registered ветка «iterate»** (закоммичена до окна): если North Star
провален (например, <5 дней или нет роста) при зелёной диагностике —
исполняется ветка iterate: трения-метрики решают, что крутить (cookie
TTL, mnd_-стена, vscode-тупики → кнопка «продолжить тему в zcode»).
Провал North Star ≠ провал проекта; провал guardrail = провал.

**Продуктовый гейт срезов 1–2:** «владелец за 60 секунд понимает, что
живо и что делалось» — фиксация скриншотом + словами владельца.

**Трения-метрики** (диагностика привычки): доля телефонных визитов с
ре-логином (порог >30% → пересмотр TTL с числами — решение владельца
(б)); mnd_-стена с объяснением; кнопка «заблокировать устройство»;
vscode-тупики как воронка — кнопка «продолжить тему в zcode» =
пост-оконный шаг при базлайне ≥3–5 тупиков/нед.

## Consequences

**Фазирование rev.2 — вертикальные срезы (контракт §4):**

| Волна | Календарь | Содержимое | Гейты |
| --- | --- | --- | --- |
| Неделя 0 — контракт-first | до кода | OpenAPI-шейпы срезов 1–3 + UI-моки; факт-чек app-server для WRITE-ноги (P0); SSH-базовая линия (ручной замер); пилотный hysteria-звонок с телефона | решения владельца (а)–(в) |
| Срез 1 — «что происходит» | день 4–5 | zcode-сканер (`mode=ro` + WAL-snapshot-fallback, анти-write-тесты); derived-реестр `(executor_id, native_id)`; список сессий в UI; экран покрытия + онбординг-карточка (3 кейса) | блокеры до UI-показа; продуктовый гейт «60 секунд» |
| Срез 2 — «что делалось» | день 8–10 | полные read-only транскрипты zcode; vscode — списки (метаданные+превью; known-gap: полный транскрипт kind:1); pi-список; `link memory_id`; дайджест-лента «активное 24ч + открытые todo + ждут владельца» | №4 полностью; диагностика видимости; продуктовый гейт |
| Шаг 1.5 — live-tail | сразу после среза 2 | read-only досматривание живой чужой сессии тем же GET-путём | transcript-serving gate |
| Срез 3 — «порулить» | неделя 2–2.5 | `vesmaro-session-relay.service`; НОВАЯ сессия с телефона — первый релейный сценарий (relay-origin, provenance-гейты не касаются); продолжение существующей — второй; чат = перечитывание хвоста стора (≤60с p95) | блокеры «дыма» до первого прогона; step-up PIN; confirm-режим |
| Retro-окно | после среза 3 | North Star + 2 guardrails; диагностика = прежние 5 гейтов | Acceptance |

До первого полезного экрана ≈ 4–5 рабочих дней; срезы 1–3 ≈ 2–2.5 недели
одного инженера. Hermes-ридер в фазу 1 не входит (known-gap до T004).
Полный транскрипт vscode — known-gap среза 2 (kind:1).

**Принятые остаточные риски (контракт §5):**

| Риск | Митигация | Почему принято |
| --- | --- | --- |
| Host integrity relay-хоста (малварь в UID стора = всё) | loopback + W4 mTLS + capability flag + аудит | тот же уровень доверия, что локальная работа сегодня |
| Компрометация борда = кросс-хостовое раскрытие транскриптов | на борде нет буфера контента (store-tail GET), redaction choke-point, ui-класс, аудит `session.transcript_viewed` | single-tenant LAN+VPN; пересмотр при любом расширении экспонирования |
| Украденный разблокированный телефон = транскрипты + typed-confirm | только own-сессии, нет inject, step-up PIN на руление (TTL ~15 мин), кнопка «заблокировать устройство», one-command ритуал | предел ущерба = own-сессии; WebAuthn — потолок расширения |
| Cookie-replay ≤ idle-TTL | стримы/GET ≤ того же TTL; вариант «7 дней + минутный отзыв» — решение владельца (б) | модель ADR 0014 + решение (б) |
| GUI+headless конкурентная запись в zcode-стор (WAL, busy_timeout) | per-session мьютекс реле | вендор-поддерживаемая схема; monitor |
| Parse-зависимость от внутренних форматов (22 миграции zcode, конверт v3 vscode, parentId pi) | read-only ридеры, капы, WAL-snapshot-fallback, трекинг миграций | потеря видимости при апгрейде ≠ порча стора |
| Рестарт relay-хоста убивает ходы mid-turn | drain-ритуал, честный UI-статус, WAL стора | дрифта нет; стор цел |
| Спуфинг `session.updated` скомпрометированным executor-токеном | ingest-binding сигналов; контент читается только из стора | деградация свежести, не подмена контента |
| Отсутствие e2e-шифрования чата | потолок v1 = lab-CA TLS; e2e требует форка харнесса (NO-DRIFT) | граница зафиксирована, не долг |

**Открытые вопросы:**

1. Владелец: решения (а)–(в) — «Страница решений владельца» ниже.
2. W4 loopback-ingress расписание — от него зависит B-нога удалённых
   хостов (при сдвиге — деградация до ноут-сторов + known-gap; экран
   покрытия показывает это честно).

## Страница решений владельца

Простым языком, без деталей. Комитет улучшил план Коры: вместо
«построим всё за 3–4 недели и покажем разом» — три коротких среза,
каждый полезен сам по себе; первый экран (список твоих zcode-сессий) —
на 4–5 день. Успех будем мерить не исправностью механизмов, а простым
вопросом: стал ли ты сам заходить в Кору.

**(а) Ратифицировать rev.2?** Да — срезы, упрощённый чат и честная
метрика снижают риск переделок. Нет — рабочим текстом остаётся rev.1.

**(б) Cookie телефона.** Сейчас сессия живёт 6 часов: зашёл утром —
вечером ре-логин.

- Вариант 1 — оставить 6 часов как есть.
- Вариант 2 — «остаться на устройстве»: 7 дней, только для спаренного
  телефона, отзыв одной кнопкой за минуту.
- Вариант 3 — WebAuthn сразу: надёжнее всех, но это отдельный проект и
  новый ритуал входа.

Рекомендация: вариант 2 — комфорт телефона плюс одноминутный отыгрыш
риска.

**(в) Имя.** «Cortex» сталкивается с внешним «Cortex Code». Нужно
проверить 2–3 запасных имени (час работы), пока имя не ушло наружу.
Рекомендация: сделать сейчас, до любого внешнего употребления имени.
