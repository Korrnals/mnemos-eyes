# Бэкап и восстановление

Всё, что накапливается в системе, лежит в нескольких SQLite-базах: задачи
борда — в `board.db` на PVC кластера, память — в `mnemos.db` и
`vectors.db` на кластере и на ноутбуке. Сбой тома, неудачный апгрейд или
случайное удаление стоят минуты бэкапа. Эта страница — как копировать,
где хранить и как вернуть на место.

## Что копировать

| База | Где живёт | Что внутри |
| --- | --- | --- |
| `board.db` | PVC борда в кластере + локальная копия на рабочей машине | задачи, история, поручения, реестр хранилищ |
| `mnemos.db` + `vectors.db` (кластер) | PVC mnemos | память кластера |
| `mnemos.db` + `vectors.db` (ноутбук) | `~/.mnemos/data` | локальная память |

Снимайте всё сразу: готовый скрипт делает это одной командой.

## Сделайте бэкап одной командой

В репозитории есть `scripts/backup-all.sh`. Он снимает согласованные
снимки всех баз через `sqlite3 .backup`, проверяет каждую копию
(`PRAGMA integrity_check`), считает контрольные суммы и пишет манифест:

```bash
scripts/backup-all.sh                  # копия за сегодня
scripts/backup-all.sh 2026-09-22       # копия с явной датой
```

Результат — каталог вида
`$VESMARO_BACKUP_ROOT/2026-09-22/` с тремя подкаталогами (`laptop`,
`cluster`, `board`), файлом `SHA256SUMS` и `MANIFEST.txt`. Каталог
копий задаётся переменной `VESMARO_BACKUP_ROOT` (по умолчанию — каталог
`backups` рядом с проектами); пути под вашу машину поправьте в шапке
скрипта.

Копия делается без остановки борда: `.backup` читает базу согласованно,
пока писатели работают.

## Копируйте регулярно

- Минимум — перед каждым обновлением борда и перед любым ручным
  вмешательством в кластер: [Обновление борда](upgrade.md).
- Хорошая привычка — ежедневный ночной прогон по расписанию:

  ```bash
  # crontab -e
  15 3 * * * /path/to/repo/scripts/backup-all.sh >> /tmp/backup-all.log 2>&1
  ```

- Храните копии на другом диске или машине: бэкап рядом с оригиналом
  переживает тот же сбой, что и оригинал.

## Восстановите базу борда

Каждый файл копии — обычная SQLite-база. Восстановление делается прямо в
живую базу через согласованную операцию `.backup` — без долгого простоя.

1. Проверьте копию перед установкой:

   ```bash
   python3 -c "import sqlite3; \
     print(sqlite3.connect('board-cluster.db') \
     .execute('PRAGMA integrity_check').fetchone())"
   ```

   Ожидается ответ `ok`.

2. Найдите под борда и загрузите копию во временный каталог:

   ```bash
   POD=$(kubectl -n kube-agents get pod \
     -l app.kubernetes.io/name=vesmaro-eyes \
     -o jsonpath='{.items[0].metadata.name}')
   kubectl -n kube-agents cp board-cluster.db "$POD":/tmp/board.db
   ```

3. Восстановите содержимое в живую базу и проверьте результат:

   ```bash
   kubectl -n kube-agents exec "$POD" -- python -c "
   import sqlite3
   src = sqlite3.connect('/tmp/board.db')
   dst = sqlite3.connect('/data/board.db')
   src.backup(dst)
   print(dst.execute('PRAGMA integrity_check').fetchone())
   "
   ```

   Ожидается `('ok',)`.

4. Перезапустите борд, чтобы все соединения открылись по восстановленной
   базе, и проверьте:

   ```bash
   kubectl -n kube-agents rollout restart deployment/vesmaro-eyes
   kubectl -n kube-agents rollout status deployment/vesmaro-eyes
   curl -ksS https://board.example.com/api/health | head -c 400
   ```

5. Откройте доску и убедитесь, что задачи и история на месте. Временный
   файл в поде можно удалить.

`helm rollback` откатывает только манифесты релиза — данные он не
восстанавливает. Восстановление данных — всегда возврат файла из копии.

## Восстановите память mnemos

Тот же порядок, другие держатели баз:

- Кластерный mnemos: скопировать `mnemos.db` и `vectors.db` из копии на
  его PVC при остановленном поде mnemos, затем поднять и проверить
  `integrity_check`. Чужой helm-релиз mnemos в это окно не трогайте.
- Ноутбучный: остановить локальный mnemos, вернуть файлы в
  `~/.mnemos/data`, запустить.

Глубже про сами базы mnemos — в импортированном ранбуке апстрима:
[бэкап и восстановление mnemos](/docs/mnemos/admin/runbooks/backup-restore).

## Учения восстановления

Бэкап, который ни разу не восстанавливали, — гипотеза. Раз в пару месяцев
проведите репетицию: поднимите копию `board.db` во временный под или на
тестовой машине, убедитесь, что доска открывается и задачи на месте,
запишите, сколько это заняло.
